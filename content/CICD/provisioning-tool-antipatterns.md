# 설치/프로비저닝 자동화 도구 안티패턴

> 클러스터 초기화·배포 자동화 CLI를 바닥부터 두 대에 돌리며 드러난 반복 결함들. 공통 근본원인은 **통합테스트 부재**.

---

## 안티패턴

### 1. `--help`가 실제 동작을 실행
- clap/argparse 없이 수동 인자 파싱을 하면 `--help`가 인식 안 돼 그대로 init/deploy가 돌아간다.
- 위험: 사용자가 "그냥 도움말 보려던" 명령이 파괴적 초기화를 실행. **테스트 삼아 `--help` 치는 것도 금물**이 되어버림.
- 교정: 인자 파서를 제대로 쓰고, 파괴적 서브커맨드는 확인 프롬프트/`--yes` 게이트.

### 2. 배포 대상 목록 하드코딩
- 배포할 노드/VM 이름을 소스에 박아두면 실제 환경 이름과 어긋나 엉뚱한 대상에 배포하거나 아무것도 안 됨.
- 교정: **런타임 발견**(예: `virsh list`, 인벤토리 조회, 서비스 디스커버리)으로 대상 목록을 얻는다.

### 3. 멱등성 체크 SSH에 `BatchMode=yes` 누락
- 재실행 시 "이미 됐나?" 확인하려고 ssh를 도는데 키가 없으면 **비번 프롬프트에서 hang** → 자동화가 무한 대기.
- 교정: 자동화용 ssh는 항상 `-o BatchMode=yes`(프롬프트 대신 즉시 실패) + 실패를 "미설정"으로 해석.

### 4. 릴리스 태그 부재로 stale 소스 배포
- git 태그가 없으면 릴리스 파이프라인(RPM/패키지 빌드)이 안 돌아 패키지가 옛 커밋에 고정됨. 설치 도구가 이 stale 패키지를 깔면 fresh 환경인데 옛 코드가 뜬다.
- 교정: 태그/버전 발행을 릴리스의 트리거로 확립. 설치 도구가 까는 버전을 로그로 노출. 최신화 경로(CI deploy)를 문서화.

## 교훈

- 네 가지 모두 "한 번은 사람이 손으로 성공시켰지만 자동 재실행에서 깨지는" 유형. **fresh 환경에서 무인 재실행하는 통합테스트**가 있었으면 전부 조기에 잡혔다.
- 자동화 도구 리뷰 체크리스트: (a) 대상을 스스로 발견하는가 (b) 안전하게 재실행되는가(멱등·BatchMode) (c) 파괴적 동작에 게이트가 있는가 (d) 까는 버전을 알 수 있는가.
