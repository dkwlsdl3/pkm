# 빌드 잡에서 시험을 선컴파일해 캐시에 넣는 최적화는 전송 비용으로 손실이 될 수 있다

> **TL;DR**: 빌드 잡이 `cargo build --tests` 로 시험 산출물까지 만들어 캐시에 넣으면 뒤따르는 시험 잡의 컴파일은 사라지지만 **캐시가 1~2GB 불어나 복원·업로드가 그만큼 늘어난다**. warm-cache 실측에서 전체 임계경로 **+2:32 순손실**이었다. 되돌릴 때는 그 줄만 지우면 안 되고 **캐시 키를 함께 바꿔** 옛 산출물을 떼어내야 한다.

## 용어

| 표기 | 원어 | 뜻 |
|---|---|---|
| 임계경로 | critical path | 파이프라인에서 가장 오래 걸리는 잡 연쇄. 이것이 줄지 않으면 개별 잡 단축은 체감이 없다 |
| warm / cold cache | — | 캐시가 채워진 상태 / 빈 상태의 실행. 첫 회는 cold 라 비교에서 뺀다 |
| `cargo build --tests` | — | 시험 바이너리까지 컴파일하되 실행은 하지 않는 옵션. `target/` 에 test cfg 산출물이 남는다 |

## 증상

- 시험 잡의 컴파일 시간은 확실히 줄었다(4패스 900초 중 실행은 138초, 나머지가 컴파일이었다)
- 그런데 파이프라인 전체는 **더 느려졌다**. 빌드 잡의 캐시 업로드와 시험 잡 두 개의 캐시 복원이 각각 늘었다

## 원인

캐시는 공짜가 아니다. 시험 산출물은 릴리스 산출물과 별개의 cfg 로 컴파일되므로 `target/` 이 거의 두 배가 되고, 그 차이가 **잡 수만큼** 전송된다(빌드 1 업로드 + 시험 잡 N 복원). 러너와 캐시 저장소 사이의 대역폭이 컴파일 속도보다 병목이면 손실이다.

이 판정은 "선컴파일이 무의미하다" 가 아니라 **"이 캐시 구성에서는 손실이다"** 다. 러너 로컬 캐시처럼 전송 비용을 줄이는 수단이 생기면 전제가 달라진다.

## 해결

```yaml
backend:build:
  cache:
    # 🔴 -v2 는 무효화 장치. 선컴파일 실험이 남긴 test cfg 산출물이 옛 키에 1~2GB 있어
    #    그 줄만 지워도 같은 키를 pull 하면 전송 시간이 줄지 않는다. 키를 바꿔야 실제로 빠진다.
    key: cargo-backend-v2
    paths: [.cargo/registry/, service/backend/target/]
  script:
    - cargo build --release
    # - cargo build --release --tests   # 2026-08-24 되돌림: warm 실측 +2:32 순손실. 다시 넣지 마라.

backend:test:
  cache:
    key: cargo-backend-v2   # ⚠️ 빌드 잡과 글자까지 같아야 공유된다. 한쪽만 올리면 빈 캐시로 전량 컴파일
    policy: pull
```

- **되돌림 = 줄 삭제 + 캐시 키 무효화.** 같은 키를 공유하는 잡 전부(빌드·pull 앵커)를 같이 바꾼다.
- **재측정 기준을 주석에 남긴다** — 동등 조건 warm 3회 중앙값, 캐시 복원·컴파일·링크·시험 실행을 분리 계측. 이것이 없으면 다음 사람이 같은 줄을 다시 넣는다.
- 측정은 실제 파이프라인으로 한다. 1회 cold 는 비교에서 빼고, 로컬 추정으로 판정하지 않는다.

> [!WARNING]
> 캐시 구성(paths·policy)을 바꿀 때마다 키 접미사도 올려라. 안 올리면 옛 내용과 새 내용이 한 키에 섞여 어느 쪽을 재는지 알 수 없다.
