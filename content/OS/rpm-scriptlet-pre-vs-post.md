# 설치를 막아야 하는 검사는 %pre 에 둔다

> **TL;DR**: RPM 스크립틀릿 중 **실패로 설치를 막을 수 있는 것은 `%pre` 뿐**이다. `%post` 의 `exit 1` 은 "서비스를 안 올린다"는 효과만 있고 **파일은 이미 교체된 뒤**다. 다만 `%pre` 실패도 "배포 중단"이 아니라 **그 패키지 하나의 교체 차단**이라, 같은 트랜잭션의 다른 패키지는 그대로 진행된다.

## 개요

- **무엇**: RPM 패키지의 설치 단계 훅 중 `%pre`(파일 교체 **전**)와 `%post`(파일 교체 **후**)의 실패 처리 차이.
- **왜 / 언제**: 업그레이드 전제조건(DB 도달, 디스크 여유, 선행 버전)을 검사해서 **못 지나가면 설치 자체를 멈추고 싶을 때**.

## 동작 / 예시

`%pre` 는 인자 `$1` 로 상황을 구분한다 — `1` 은 신규 설치, `2` 이상은 업그레이드다.

```spec
%pre
if [ "${1:-1}" -ge 2 ]; then
    # 업그레이드다. %post 의 가용성 검사와 같은 사용자·같은 소켓으로 본다.
    if ! command -v psql >/dev/null 2>&1 || \
       ! sudo -u postgres psql -d postgres -c "SELECT 1" >/dev/null 2>&1; then
        echo "ERROR: 업그레이드인데 PostgreSQL 에 접속하지 못했다 — 설치를 진행하지 않는다" >&2
        echo "       파일을 바꾸기 전인 지금 멈춘다. 옛 버전이 그대로 남는다." >&2
        exit 1
    fi
fi
```

`%post` 에서 같은 검사를 하면 **이미 새 바이너리가 깔린 뒤**다. 마이그레이션을 적용하지 못한 채 새 코드가 옛 스키마 위에 올라가고, rpm 은 그것을 되돌리지 못한다.

## 주의

> [!WARNING]
> **`%pre` 실패는 「이 패키지의 교체 차단」이지 「트랜잭션 중단」이 아니다.** 같은 `dnf` 명령으로 여러 패키지를 갱신하면 나머지는 그대로 진행된다 — 새 도구 + 옛 서비스 조합이 남을 수 있다. 서비스 자체는 옛 바이너리 + 옛 스키마로 정합하지만 **패키지 의존 관계는 어긋난 상태**이므로, 낸 실패를 그냥 넘기지 말고 전제를 고친 뒤 같은 갱신을 다시 돌려야 한다.

> [!NOTE]
> 이 규칙은 **실제 rpm 트랜잭션으로 매번 다시 재는 편이 안전하다.** 배포판·rpm 버전마다 다를 여지가 있어 문서만 믿기보다 검증 스크립트를 저장소에 두고 CI 가 돌리게 했다.
