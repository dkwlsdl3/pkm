# 다른 파일시스템으로 옮길 때 보존해야 하는 것들

> **TL;DR**: 같은 파일시스템 안의 이동은 `rename()` 한 번이라 메타데이터가 그대로 따라간다. **경계를 넘는 순간 복사+삭제로 바뀌면서** 소유자·특수 권한 비트·심볼릭 링크 대상·덮어쓸 파일의 inode 가 조용히 달라진다. 옮기기 전과 후가 같은지 시험으로 잠가야 한다.

## 증상

- 이동 후 파일 주인이 **작업을 실행한 프로세스 계정**으로 바뀌어 있다.
- 공유 디렉터리로 옮긴 파일에서 **set-group-ID 비트가 사라져** 그룹 상속이 끊긴다.
- 심볼릭 링크를 옮겼더니 링크가 아니라 **가리키던 파일의 복사본**이 생긴다.
- 기존 파일을 덮어쓰는 이동 뒤에 그 파일을 열고 있던 프로세스가 옛 내용을 계속 본다(또는 하드링크가 끊긴다).
- 같은 이름이 있는데 **확인 없이 덮어써서** 원본이 사라진다.

## 원인

`rename(2)` 는 **같은 파일시스템 안에서만** 동작하고, 경계를 넘으면 `EXDEV` 를 돌려준다.
많은 구현이 여기서 조용히 "복사 후 원본 삭제"로 대체하는데, 이때 보존은 전부 수동이다.

```text
rename(src, dst)  →  EXDEV
  ↓ 대체 구현
open(dst, O_CREAT)   ← 소유자 = 실행 계정, 권한 = mode & ~umask
copy bytes
unlink(src)          ← 여기서 실패하면 두 곳에 남는다
```

## 해결

경계를 넘는 경로에서 **명시적으로** 맞춰야 하는 목록:

- **소유자·그룹** — `fchown`. root 권한이 없으면 보존 불가라는 것을 실패로 알린다(조용히 넘어가지 않는다).
- **권한 비트 전체** — setuid/setgid/sticky 포함. `mode & 0777` 만 복사하면 특수 비트가 날아간다.
- **심볼릭 링크** — 따라가지 말고 링크 자체를 재생성한다(`readlink` → `symlink`).
- **덮어쓰기 대상** — 지우고 새로 만들지 말고 **있던 파일에 쓴다.** inode 가 유지돼야 열려 있는 핸들·하드링크가 살아 있다. 이때도 주인은 바꾸지 않는다.
- **이름 충돌** — 덮어쓰기 전에 확인을 받는다. 배치 작업이면 **덮어쓸 수 없는 충돌**을 별도 사유로 구분해 보고한다.
- **원본 삭제 실패** — 복사는 됐고 삭제가 실패한 상태를 성공으로 보고하지 않는다.

가능하면 대체 구현을 직접 짜지 말고 `mv`·`rsync -aHAX --remove-source-files` 처럼
보존 규칙이 이미 정의된 도구에 맡긴다.
