# 검사한 경로와 실제로 쓰는 경로가 다르면 그 검사는 무효다

> **TL;DR**: 파일 저장소가 이름 충돌을 피해 `foo.txt` → `foo (1).txt`로 자리를 비켜 갈 때, 권한 검사를 **요청한 이름**으로 하고 저장은 **비켜 간 이름**에 하면 그 검사는 아무것도 보장하지 않는다. 저장이 고를 이름을 **먼저 확정한 뒤 그 경로만** 검사한다.

---

## 증상

같은 결함이 방향만 다르게 두 가지로 나타난다.

| 방향 | 증상 |
|---|---|
| **우회** | `/dir/foo.txt`에는 쓸 권한이 있고 `/dir/foo (1).txt`에는 제한이 걸려 있는데, 충돌이 나서 비켜 간 그 자리에 **검사 없이** 써진다 |
| **과잉 차단** | 실제로는 만들지도 않을 `/dst/foo`의 제한 때문에 `/dst/foo (1)`로 갈 복사가 거절된다 |

우회 쪽만 보면 "권한 검사가 없다"로 읽히고, 과잉 차단 쪽만 보면 "권한 검사가 너무 빡세다"로 읽힌다. 원인은 하나다.

## 원인

**검사 시점의 경로 ≠ 쓰기 시점의 경로.**

자리를 비켜 주는 코드(`resolve_conflict_name` 류)는 대개 저장 직전에 실행되는데, 권한 검사는 요청을 받자마자 실행된다. 그 사이에 경로가 바뀌면 검사는 존재하지 않는 대상에 대한 것이 된다.

이 모양이 나타나는 자리는 **자리를 비켜 주는 곳 전부**다. 하나만 고치면 나머지가 남는다.

- 파일 복사·이동 (대상 이름 충돌)
- 휴지통 복원 (원래 자리가 이미 차 있음)
- 업로드 — 일반 업로드와 청크 업로드가 **각각** 같은 형태를 가진다

## 해결

**저장이 고를 이름을 먼저 정하고, 그 경로만 검사한다.** 요청 경로의 권한은 보지 않는다.

```rust
// 나쁨: 요청 경로를 검사하고, 저장은 다른 이름에 한다
verify_permission(&requested_path)?;
let final_path = resolve_conflict_name(&requested_path);  // 여기서 경로가 바뀐다
write(&final_path, data)?;

// 좋음: 최종 경로를 먼저 정하고 그것만 검사한다
let final_path = resolve_conflict_name(&requested_path);
verify_destination_with(&final_path)?;
write(&final_path, data)?;
```

- 검사와 이름 결정을 **하나의 관문 함수 안**에 넣어 순서가 다시 갈라지지 않게 한다
- 충돌 전략(`rename`/`overwrite`/`fail`) 파싱이 권한 검사보다 **뒤에** 있으면 이름을 미리 고를 수 없다 — 파싱을 앞으로 옮긴다
- 상위 폴더 생성 같은 부수 효과도 **검사 뒤로** 미룬다. 쓸 권한이 없는 자리에 빈 폴더만 남는 것을 막는다

## 왜 놓치기 쉬운가

이 결함은 **권한 검사 코드를 아무리 들여다봐도 안 보인다.** 검사 자체는 올바르게 작성돼 있기 때문이다. 보려면 검사 지점과 쓰기 지점 사이에 경로를 바꾸는 코드가 있는지를 봐야 한다 — 즉 **검사가 아니라 그 둘 사이를 읽어야** 한다.

같은 이유로, 권한 관련 결함을 하나 고칠 때는 **"검사한 값과 실제로 쓰는 값이 같은가"를 전 경로에 대해** 물어야 한다. 경로뿐 아니라 사용자 ID, 대상 리소스 ID에도 같은 질문이 성립한다.
