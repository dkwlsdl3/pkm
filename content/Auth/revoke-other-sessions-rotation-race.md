# 다른 세션 로그아웃은 현재 세션을 무엇으로 식별하는가에서 갈린다

> **TL;DR**: "다른 기기에서 로그아웃" 을 만들려면 먼저 **현재 세션을 확실히 식별**해야 하는데, 대개 그 단서는 리프레시 쿠키 하나뿐이다. 쿠키가 없으면 **거부**하고, 제외 조건은 **토큰 회전 경합**을 고려해야 한다 — 안 그러면 자기 세션이 죽는다.

## 증상

- "다른 기기 로그아웃" 을 눌렀는데 **자기도 로그아웃**된다
- 특히 여러 탭을 켜 두었거나 방금 토큰이 갱신된 직후에 재현된다

## 원인

**하나 — "기기" 를 식별할 수단이 없다.** User-Agent 와 IP 는 위조 가능하고 바뀌며, 같은 기기의 여러 브라우저를
구분하지 못한다. 실제로 서버가 식별할 수 있는 단위는 **세션(리프레시 토큰 행)** 이다. 이름을 "기기" 로
지으면 사용자가 없는 보증을 기대하게 된다.

**둘 — 회전 경합.** 리프레시 토큰을 갱신 때마다 회전시키는 구현에서, "현재 토큰만 빼고 전부 폐기" 를
단순 비교로 짜면 이런 일이 생긴다.

```text
t0: 사용자가 "다른 세션 로그아웃" 요청 — 쿠키의 토큰 = R1
t0+ε: 다른 탭의 자동 갱신이 먼저 도착 — R1 폐기, R2 발급
t1: 서버가 "R1 이 아닌 것 전부 폐기" 실행 → R2 도 폐기됨 → 현재 세션 사망
```

제외 조건을 **토큰 값**이 아니라 **세션 계보(session/family id)** 로 잡아야 회전을 견딘다.

## 해결

```text
1. 리프레시 쿠키가 없으면 → 거부한다 (401/400).
   "쿠키가 없으면 전부 폐기" 같은 폴백은 사용자가 의도하지 않은 결과다.
2. 쿠키의 토큰에서 세션 계보 id 를 찾는다.
3. 그 계보에 속한 행만 남기고 나머지를 폐기한다 — 값 비교가 아니라 계보 비교.
4. 폐기와 조회를 같은 트랜잭션에서, 갱신된 행 수를 응답에 싣는다.
```

- 회전 구조가 없다면(토큰이 고정이면) 값 비교로 충분하지만, 그 경우 별도의 탈취 위험을 안는다
- **재인증(비밀번호 재확인)을 넣을지는 별도 결정이다.** 넣지 않기로 했다면, 세션을 탈취한 공격자가
  정당한 사용자를 쫓아낼 수 있다는 **위협 모델을 명시로 수용**하고 문서에 남긴다 — 빠뜨린 것과
  받아들인 것은 다르다
- 시험은 "폐기됐다고 표시되는가" 가 아니라 **폐기된 토큰으로 실제 갱신이 거부되는가**를 확인해야 한다
