# 권한 카테고리 정본은 사용자에게 보이는 메뉴 구조

> **TL;DR**: RBAC 권한 카테고리를 백엔드 모듈 경로(기술 렌즈)로 매기면, 관리자가 **실제로 역할을 부여하는 단위**(화면 메뉴)와 어긋난다. 카테고리 정본은 프론트 사이드바 메뉴 구조로 두고, DB CHECK 제약과 그 목록을 일치시킨다.

## 개요

- **무엇**: 권한을 묶는 카테고리(그룹)를 무엇을 기준으로 정의할지에 대한 결정
- **왜 / 언제**: 라우트가 많아 권한을 개별로 줄 수 없을 때 카테고리 단위로 부여하게 된다. 이때 카테고리 축이 화면과 다르면, 관리자가 "이 메뉴를 쓰게 해달라"는 요청을 권한 조합으로 번역하지 못한다

## 두 렌즈가 어긋나는 방식

같은 기능을 어디에 넣을지가 렌즈에 따라 갈린다.

| 기능 | 백엔드 기술 렌즈 | 메뉴(사용자) 렌즈 |
|---|---|---|
| 스냅샷 / 아카이브 | 스토리지 모듈 → `storage` | 데이터보호 메뉴 → `protection` |
| VM 관리 | 디바이스 제어 모듈 → `device` | 시스템 메뉴 → `system` |
| 외부 연동(수집) | 한 모듈이라 `system` 하나 | **3분할** — 수집통계=대시보드 / 데이터·엔티티=디바이스 / 동기화=데이터보호 |

기술 렌즈는 "코드가 어디 있나"를, 메뉴 렌즈는 "누가 무엇을 할 수 있나"를 답한다. 권한은 후자의 질문이다.

## 결정 규칙

1. **카테고리 정본 = 프론트 사이드바 메뉴 목록** (예: `layouts/admin.vue`의 메뉴 정의)
2. 그 목록을 DB 마이그레이션의 `CHECK` 제약으로 고정해 임의 문자열 유입을 막는다
3. 설계문서의 분류가 메뉴와 다르면 **설계문서를 정정**한다 (코드/화면이 이긴다)
4. 한 백엔드 모듈이 여러 메뉴에 걸치면 **모듈을 쪼개지 말고 라우트 단위로 서로 다른 카테고리**를 부여한다

```sql
-- 카테고리 집합을 정본 목록으로 못박는다
ALTER TABLE permissions
  ADD CONSTRAINT permissions_category_check
  CHECK (category IN ('dashboard','device','storage','protection','system','network','account'));
```

> [!WARNING]
> 메뉴가 개편되면 카테고리도 함께 바뀐다. 메뉴 = 정본이라는 결정은 "메뉴 변경 시 마이그레이션이 필요하다"는 비용을 받아들이는 것이다. 대신 라우트 ↔ 카테고리 매핑 누락은 CI에서 막는다([[route-inventory-syn-ast]]).
