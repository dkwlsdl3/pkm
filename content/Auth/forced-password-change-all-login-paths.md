# 비밀번호 변경 강제는 모든 로그인 경로에서 집행해야 한다

> **TL;DR**: 관리자가 임시 비밀번호로 재설정하고 "다음 로그인 때 변경"을 걸었다면, 그 강제는 비밀번호 로그인만이 아니라 **패스키 등 모든 로그인 경로**, 그리고 **재설정 직전에 이미 시작된 로그인**에도 적용돼야 한다. 한 경로라도 빠지면 관리자가 아는 임시 비밀번호가 계속 유효한 채로 남는다.

## 증상

- 관리자 재설정 기능을 만들고 비밀번호 로그인 경로에는 "변경 화면으로 보내기"를 넣었다.
- 그런데 **패스키 로그인**은 계정 상태(활성 여부)만 보고 토큰을 줘서, 변경 강제를 건너뛰었다.
- 재설정 **직전에** 시작된 로그인(비밀번호 확인 → 메일 인증 코드 대기 중)은 재설정 뒤에도 세션을 발급받을 수 있었다. 독립 리뷰에서 BLOCK으로 잡혔다.

## 원인

- 플래그 검사가 "비밀번호 확인" 단계에만 붙어 있었다. 집행 지점이 경로마다 따로 있었던 것이다.
- 로그인 발급(인증 코드 확인 → 세션 생성)과 재설정이 서로 잠금 없이 돌아, 재설정 전에 확인된 상태로 발급이 끝났다.

## 해결

- **집행은 세션·토큰을 발급하는 단 한 곳**에서 한다. 경로(비밀번호·패스키·OTP)마다 검사를 복사하지 않는다.
- 재설정 시 **이미 발급된 인증 코드·대기 중 로그인을 만료**시킨다.
- 재설정과 발급을 직렬화한다. 사용자 행을 잠그고, 발급 직전에 상태(변경 필요 여부, 재설정 시각)를 다시 읽는다.
- 패스키 처리 방침은 선택지가 둘이다. 실제로는 **임시 비밀번호를 바꿀 때까지 패스키 로그인을 차단**하기로 했다.

| 방식 | 내용 |
|---|---|
| SSO식 | 비밀번호를 아무도 모르는 값으로 바꾸고 재설정 링크를 보낸다 |
| 차단식 | 변경 전까지 다른 경로를 403으로 막는다(API 키 비활성처럼) |

```sql
-- 발급 직전 재확인(개념)
SELECT must_change_password, password_reset_at FROM users WHERE id = $1 FOR UPDATE;
-- 인증 코드 생성 시각 < password_reset_at 이면 거부
```
