# 공개 링크의 수명은 만든 사람의 계정 상태에 매단다

> **TL;DR**: 인증 없이 토큰만으로 접근되는 공개 링크는 **만든 사람이 탈퇴·정지·가입 거절돼도 그대로 열려 있다.** 링크 자체의 만료만 보지 말고, 공개 경로에서 **소유자의 현재 계정 상태를 매번 확인**해야 한다. 단, 개인 소유가 아닌 자원은 판별자가 다르다.

## 증상

- 퇴사 처리한 계정이 만든 공유 링크로 **여전히 파일이 받아진다**
- 가입이 거절된 신청자가 심사 중에 만든 링크가 살아 있다
- 계정을 지웠는데 링크 목록에서만 사라지고 **공개 경로는 동작**한다

## 원인

공개 링크는 **발급 시점의 스냅샷**이고, 계정 상태는 그 뒤에 바뀐다. 링크 테이블에 `expires_at` 과
`is_active` 는 있어도 **소유자의 생존 여부를 참조하는 조건이 없다.**

여기에 두 가지가 겹친다.

1. 계정 삭제·탈퇴 처리가 **자기가 만든 링크를 끄는 단계를 빠뜨린다**
2. 공개 조회 쿼리가 링크 행만 읽고 사용자 테이블을 **JOIN 하지 않는다**

## 해결

**둘 다 한다 — 상태 변경 시 정리 + 조회 시 게이트.** 한쪽만으로는 이미 새고 있는 링크를 못 막거나
(정리만), 정리 안 된 잔재가 쌓인다(게이트만).

```sql
-- 공개 조회: 소유자 상태를 INNER JOIN 으로 물린다
SELECT l.*
  FROM share_links l
  JOIN users u ON u.id = l.owner_id      -- LEFT JOIN 이면 소유자가 없어도 통과한다
 WHERE l.token = $1
   AND l.is_active
   AND u.status = 'active';
```

> [!WARNING]
> **`LEFT JOIN` 을 쓰면 게이트가 무력화된다.** 소유자 행이 없어도 링크 행이 그대로 나온다. 조건을
> `WHERE` 가 아니라 `ON` 절에 붙여도 같은 결과다. 게이트 목적의 조인은 반드시 `INNER JOIN`.

**개인 소유가 아닌 자원은 판별자가 다르다.** 그룹·공용 폴더의 링크는 만든 사람이 나가도 살아 있어야
자연스럽다. 이때 수명을 매다는 대상은 **사람이 아니라 그 폴더**다. 어떤 링크가 어느 쪽인지는
`group_id` 같은 필드가 아니라 **자원의 저장 유형**으로 갈리는 경우가 많으니, 판별자를 코드에서 확인하고
갈라야 한다.

**거부 사유를 응답 본문으로 흘리지 않는다** — 통과 못 한 링크는 없는 링크와 같은 답을 낸다.
