# 자격증명 변경은 원본 파괴 — 백업 먼저

## 사고 패턴

비밀번호 해시 UPDATE는 **원본을 파괴하는 비가역 작업**이다. "이 비번이 맞을 텐데 401이 나네 → 그 값으로 리셋하자"는 흐름은, 그 비번이 **다른 계정의 것**이었을 때 멀쩡한 계정의 자격증명을 날린다.

## 최소 안전장치

1. **대상 확인**: 전달받은 자격증명이 어느 계정 것인지 변경 전에 1줄 확인
2. **백업**: `UPDATE` 전에 기존 해시를 `SELECT`로 떠서 보관 — 롤백이 UPDATE 한 줄이 된다
   ```sql
   SELECT password_hash FROM users WHERE email='...';  -- 먼저
   UPDATE users SET password_hash='...' WHERE email='...';
   ```
3. **정본 위치 파악**: dev 환경 관리자 비번처럼 어딘가에 기록된 정본(e2e env 등)이 있으면 복구 가능하지만, 정본이 없는 계정은 복구 불가

## 곁가지

- 로그인 rate-limit 잠금은 시도 기록 테이블 삭제로 해제 (e2e가 같은 이유로 setup에서 초기화)
- 셸에서 비밀번호 전달 시 `-d "...$PW..."`는 `$`·`"`·백틱에서 깨진다 — `jq -n --arg`로 JSON을 만들면 인용 문제가 원천 차단됨
