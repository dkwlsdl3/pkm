# 비활성 리소스와 없는 리소스의 404 가 다르면 존재가 새어 나간다

> **TL;DR**: "꺼진 공유 링크" 와 "없는 토큰" 이 서로 다른 404 본문을 내면, 공격자는 응답 차이만으로 **토큰이 실제로 존재했는지** 알 수 있다. 인증 없는 공개 경로에서는 두 응답의 **상태코드·본문·헤더·응답시간**을 같게 만들어야 한다.

## 증상

- 무작위 토큰: `{"error":"not found"}`
- 비활성화된 실제 토큰: `{"error":"link is disabled"}`

친절한 오류 메시지가 그대로 **존재 여부 오라클**이 된다. 토큰 공간을 훑으면 유효했던 토큰만 걸러낼 수 있고,
그 값은 로그·북마크·프록시 기록에서 다시 살아날 수 있다.

## 원인

**정보 노출은 "누가 볼 수 있는가" 로 결정되는데, 응답 문구는 대개 개발 편의로 결정된다.** 인증된 경로에서는
구체적인 오류가 도움이 되지만, 인증이 아예 없는 공개 경로에서는 **같은 문구가 미인증 사용자에게
데이터베이스를 질의해 준다.**

이 함정은 열거(enumeration) 취약의 일반형이다 — 로그인의 "없는 계정" vs "비밀번호 틀림", 비밀번호 재설정,
초대 코드 확인에서 똑같이 나온다.

## 해결

공개 경로의 부정 응답을 **하나로 통일한다.**

```rust
// 없는 토큰 / 비활성 / 만료 / 소유자 탈퇴 — 전부 같은 응답
fn public_not_found() -> Response {
    (StatusCode::NOT_FOUND, Json(json!({"error": "not_found"}))).into_response()
}
```

- 상태코드뿐 아니라 **본문과 헤더까지** 같아야 한다
- 사유는 **서버 로그에만** 남긴다 (운영은 로그로 진단한다)
- 인증된 관리 화면에서는 구체적인 사유를 보여도 된다 — 경계는 **인증 여부**다
- 응답 시간 차이가 크면 그것도 오라클이 된다. DB 조회 후 분기하는 구조라면 대개 문제없지만, 조회 자체를
  건너뛰는 빠른 경로가 있다면 주의한다

> [!WARNING]
> "숨겨진 URL" 은 인증이 아니다. 토큰만으로 접근되는 자원은 그 토큰이 유효했다는 사실조차 비밀이다.
