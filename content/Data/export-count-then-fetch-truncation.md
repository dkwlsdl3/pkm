# 건수를 센 뒤 조회하는 내보내기는 조용히 잘린다

> **TL;DR**: `SELECT count(*)`로 "상한 이내"를 확인하고 그다음 행을 읽어 CSV로 내보내면, 두 문장 사이에 들어온 행 때문에 **상한을 넘은 결과가 잘린 채 정상 응답으로 나간다.** 오류도 경고도 없다. 판정을 한 곳으로 모으고, **상한+1건을 읽어** 초과를 실제로 감지한 뒤 잘림을 응답에 드러내라.

---

## 증상

- 내보낸 CSV의 행 수가 화면 필터 결과보다 적다. 응답 코드는 200이다.
- 조용한 시간대에는 재현되지 않고, 쓰기가 활발할 때만 어긋난다.
- 받은 사람은 잘렸다는 사실을 알 방법이 없다 — 파일에 아무 표시도 없다.

## 원인

세 걸음이 원자적이지 않다.

```text
1) SELECT count(*) WHERE <필터>      → 9,980 건
2) 9,980 ≤ 10,000 이므로 "전량 내보내기 가능" 판정
   ← 이 사이에 30건이 들어온다
3) SELECT ... WHERE <필터> LIMIT 10000 → 10,000 건만 읽힘 (실제 10,010건)
```

[[non-atomic-counter-limit]]과 같은 TOCTOU(Time Of Check to Time Of Use, 검사 시점과 사용 시점의 틈) 구조지만, 결과가 다르다. 카운터 상한은 **초과를 허용**하는 쪽으로 틀리고, 내보내기는 **데이터를 소리 없이 버리는** 쪽으로 틀린다. 후자가 더 나쁘다 — 잘린 CSV는 감사·정산 근거로 그대로 쓰인다.

판정 로직이 두 군데(핸들러의 사전 검사, 쿼리의 `LIMIT`)로 갈려 있으면 문제는 더 굳는다. 한쪽 상한만 바꾸면 두 값이 어긋나고, 어긋난 것을 알려주는 시험은 없다.

## 해결

**하나. 세지 말고 한 건 더 읽어라.** 상한이 N이면 `LIMIT N+1`로 조회한다. N+1건이 오면 초과가 **확정 사실**이다 — 추정이 아니다.

```sql
-- 상한 10,000
SELECT ... WHERE <필터> ORDER BY id LIMIT 10001;
```

**둘. 초과를 어떻게 다룰지 정하고 그 자리를 하나로 둔다.**

- 거부: 413/400으로 응답하고 "필터를 좁히라"고 안내 → 잘린 파일이 나가지 않는다.
- 허용하되 표시: 헤더나 마지막 행에 잘림을 명시. 다만 CSV는 표시가 떨어져 나가기 쉽다([[benchmark-invalid-value-quarantine]]와 같은 이유).
- 스트리밍: 상한 자체를 없애고 커서로 흘려보낸다. 메모리 상한만 관리하면 된다.

**셋. 상한 판정을 한 함수로 모으고 시험을 CI에 건다.** 사전 검사와 쿼리 상한이 별개로 살아 있으면 언젠가 갈린다([[adoption-gate-weaker-than-runner]]와 같은 구조).

**넷. 정렬을 못박는다.** `ORDER BY`가 없으면 어느 N건이 잘려 나갈지도 실행마다 다르다.

## 확인 방법

내보내기 도중 행을 밀어 넣는 시험을 만든다. 상한 근처에서 동시 삽입을 걸고, 결과가 **거부되거나 잘림 표시가 붙는지** 본다. 통과하는 시험이 아니라 **잘림이 감지되는지**를 보는 시험이어야 한다([[mutation-check-test-effectiveness]]).
