# 정렬키가 겹치면 페이지 경계에서 행이 중복되거나 빠진다

> **TL;DR**: `ORDER BY created_at` 처럼 **유일하지 않은 값 하나로만** 정렬하고 `LIMIT/OFFSET` 이나 커서로 나누면, 같은 값을 가진 행들의 순서가 쿼리마다 달라져 **경계에서 어떤 행은 두 페이지에 나오고 어떤 행은 어디에도 안 나온다.** 정렬키에 유일한 타이브레이커(보통 PK)를 반드시 덧붙인다.

## 증상

- 목록을 넘기다 보면 같은 항목이 두 번 보이고, 전체 건수와 실제로 본 건수가 안 맞는다.
- 일괄 등록·마이그레이션처럼 **여러 행이 같은 타임스탬프**를 갖는 데이터에서만 재현된다.
- 재현이 불규칙해서 "가끔 그런다"로 남는다.

## 원인

SQL 은 정렬키가 같은 행들 사이의 순서를 **보장하지 않는다.** 실행 계획·병렬도·캐시 상태에
따라 매번 달라질 수 있고, 페이지마다 쿼리를 새로 던지면 그 사이에 순서가 바뀐다.

```text
전체: A(10:00) B(10:00) C(10:00) D(10:01)
1페이지(LIMIT 2): A B
2페이지(OFFSET 2 LIMIT 2): 이번엔 B C 로 나올 수 있다
  → B 중복, A 는 2페이지에 없고 C 는 1페이지에 없었다
```

## 해결

```sql
-- 유일한 타이브레이커를 정렬키에 포함
ORDER BY created_at DESC, id DESC

-- 커서(keyset) 페이지네이션도 같은 튜플로 비교
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT $3;
```

- 복합 조건은 `(a, b) < (x, y)` **행 비교**로 쓴다. `a < x OR (a = x AND b < y)` 로 풀어 쓰면 인덱스를 못 타는 경우가 있다.
- 정렬키 순서와 동일한 복합 인덱스를 둔다.
- `OFFSET` 방식은 타이브레이커를 넣어도 **페이지 사이에 삽입/삭제가 일어나면** 여전히 밀린다. 목록이 계속 바뀌는 화면은 커서 방식으로 간다.

## 주의

> [!WARNING]
> 이 문제는 **화면 상한과 함께 나타나기 쉽다.** 목록 API 가 기본 20건만 주는데 화면이 "전량"으로 가정하면, 21번째부터는 아예 없는 것으로 취급된다(가입한 부서가 미가입으로 보이는 식). 상한과 전량 수집 중 어느 쪽인지 화면마다 명시한다. → [[export-count-then-fetch-truncation]]
