# 스키마를 바꾸는 동안 그것을 읽는 서비스는 내려가 있어야 한다

> **TL;DR**: 마이그레이션을 별도 배포 단계로 떼어내면서 **소비자 정지가 따라오지 않으면** 구 코드가 새 스키마를 보는 창이 열린다(실측 약 6초). 상주 writer 는 강한 잠금 DDL(Data Definition Language, 스키마를 바꾸는 SQL)의 경합 상대이기도 하다. 정지는 스키마 적용 단계가 맡고, **다시 켜는 것은 새 바이너리를 설치한 단계의 몫**이다.

## 증상

- 배포 중 수 초간 구 바이너리가 새 스키마를 읽어 오류를 낸다.
- 마이그레이션이 잠금을 얻지 못해 실패한다 — 상주 서비스가 다중문 트랜잭션을 물고 있다.
- 스키마 적용 잡이 끝나면서 서비스를 되살리는데, 그 시점의 바이너리는 아직 **구 버전**이다.

## 원인

배포를 단계로 나누면 "스키마 적용"과 "코드 배포"가 다른 잡이 된다. 정지 명령이 뒤 단계의 배포 잡 안에만 남아 있으면 순서가 이렇게 된다.

```
deploy:schema    → 마이그레이션 적용            ← 이때 구 코드가 살아 있다 (창이 열림)
deploy:services  → 정지 → 새 바이너리 설치 → 기동
```

정지가 앞으로 와야 창이 닫힌다.

```
deploy:schema    → 정지 → 마이그레이션 적용     ← 되살리지 않는다
deploy:services  → 새 바이너리 설치 → 기동      ← 켜는 것은 여기
```

## 해결

- **정지는 스키마를 건드리기 전에.** 그 대상에는 상주 데몬처럼 눈에 덜 띄는 writer 도 포함된다.
- **되살리는 것은 스키마 잡이 하지 않는다.** 그 잡이 다시 켜면 **구 바이너리가 새 스키마 위에서 돈다** — 없애려던 바로 그 상태다.
- **스키마 적용을 시작한 뒤에는 자동 복구하지 않는다(fail-closed).** 실패가 "구 스키마가 그대로다"를 뜻하지 않기 때문이다. 앞 파일이 적용되고 뒤에서 실패할 수 있고 실행기는 되돌리지 않는다. 그 상태에서 구 바이너리를 켜는 것이 가장 나쁘다 — 배포가 실패하면 서비스는 내려간 채 남는 편이 조용한 오작동보다 낫다.

CI 설정으로 이 순서를 강제한다면, 그 계약을 시험으로 잠근다.

```rust
// 잡 블록을 `script` 와 `after_script` 로 갈라서 본다.
// 🔴둘을 섞어 보면 판정이 뒤집힌다 — `after_script` 에는 되살리는 `start` 가 의도적으로 있고,
//   `script` 에는 있으면 안 된다. 한 덩어리로 찾으면 그 구분이 사라진다.
// ⚠️주석은 걷어낸다 — 설명문에 명령어가 흔히 등장한다.
```

> [!WARNING]
> **이 시험이 증명하지 못하는 것을 적어 둬라.** 대상 목록의 완전성, 실제 권한, 파이프라인 취소 신호, 러너 장애, 기동 성공은 **정적으로 알 수 없다.** 실제 파이프라인에서 겹침·취소·부분 실패로 따로 확인해야 한다.

> [!NOTE]
> 정지 계약을 검사하는 시험은 **방어를 한쪽만 지워도 깨져야** 한다. 실제로 한쪽만 지웠을 때 초록이던 시험이 두 번 나왔다 → [[mutation-check-test-effectiveness]]
