# 런타임 SQL 은 빌드가 검증하지 않는다

> **TL;DR**: 문자열로 조립되거나 파일에서 읽히는 SQL 은 컴파일러가 보지 않는다. 마이그레이션이 컬럼을 지워도 **코드는 그대로 빌드되고**, 그 경로를 태우는 시험이 없으면 API 종단점이 **죽은 채로 배포된다**. 빌드 통과는 "대상이 존재한다" 는 뜻이 아니다.

## 증상

- 빌드도 초록, 단위시험도 초록인데 **특정 종단점만 500 또는 빈 응답**을 낸다
- 오류가 로그에만 남거나, 폴백 때문에 **아예 안 남는다** (빈 목록, 기본값)
- DB 에서 같은 SQL 을 직접 돌리면 `column "..." does not exist` 가 뜬다
- 마이그레이션을 되짚어 보면 그 컬럼은 **몇 달 전에 지워졌다**

## 원인

컴파일 시점 검증이 있는 SQL(예: sqlx `query!` 매크로)과 없는 SQL(`query()`·`query_as()` 에 넘기는 문자열,
별도 `.sql` 파일, ORM 의 raw 쿼리)이 한 코드베이스에 **섞여 있다**. 앞의 것만 스키마와 대조되고 뒤의 것은
런타임에야 깨진다.

여기에 두 가지가 겹치면 결함이 조용해진다.

1. **폴백** — `try_get(...).ok()`, `unwrap_or_default()` 가 오류를 기본값으로 접는다
2. **그 경로를 태우는 시험 부재** — `--lib` 만 도는 단위시험은 종단점을 안 지나간다

## 해결

**첫째, 스키마 대조 검사를 CI 에 건다.** 코드가 참조하는 컬럼 집합과 마이그레이션 적용 후의 실제 스키마를
기계적으로 비교한다. 사람의 주의력에 맡기면 반드시 다시 새어 나온다.

```bash
# 현재 스키마 덤프와 코드가 쓰는 식별자를 대조하는 형태
pg_dump --schema-only -t 'public.*' "$DATABASE_URL" > /tmp/schema.sql
grep -rhoE '"[a-z_]+"' src/query/ | sort -u > /tmp/used-columns.txt
# 둘의 차집합이 비어 있는지 확인 (검사 스크립트로 만들어 CI 잡에 건다)
```

**둘째, 종단점을 태우는 통합 시험을 붙인다.** 컴파일러가 안 보는 계약은 시험이 보게 만들거나 아무도 안 본다.

**셋째, 폴백을 걷어낸다.** "컬럼이 없다" 와 "값이 NULL" 은 다른 사건이다. 앞의 것은 결함이므로 터져야 한다.

> [!WARNING]
> 마이그레이션을 건드린 커밋에서 `cargo build` 만 초록인 것을 근거로 삼지 말 것. 스키마를 바꿨으면
> **종단점 시험을 전량 실행**해야 하고, `#[ignore]` 가 붙은 것까지 강제로 돌려야 한다.
