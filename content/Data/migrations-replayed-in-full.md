# 마이그레이션을 매 실행 전량 재실행하는 모델의 함정

> **TL;DR**: 실행기가 "적용분 스킵"을 하지 않고 **001부터 전량 재실행**하는 구조라면, 뒤 파일이 앞 파일의 전제를 제거하는 순간 ①앞 파일이 실패하거나 ②더 나쁘게 **앞 파일 재실행이 뒤 파일 효과를 조용히 되돌린다**(`CREATE OR REPLACE FUNCTION`). 앞 파일의 해당 블록을 **전제 존재 검사로 감싸고**(트리거만이 아니라 **함수까지**), 재실행 경로가 몇 개인지 세라.

---

## 증상

- 뒤 마이그레이션이 컬럼을 제거했는데, 다음 배포 후 트리거·함수가 **옛 구현으로 되돌아가 있다**
- 또는 앞 마이그레이션이 "컬럼 없음" 오류로 실패해 배포가 멈춘다
- 로컬에서는 잘 되는데 CI 배포나 패키지 업데이트 경로에서만 깨진다

## 원인

실행기가 적용 이력 테이블에 **기록만 하고 실행 전에 조회하지 않는** 구조. 이 모델에서 마이그레이션은 "불변 이력"이 아니라 **매번 처음부터 돌아가는 멱등 스크립트 모음**이다.

그래서 파일 간 시간 순서가 **런타임에서는 보장되지 않는다** — 033이 컬럼을 지운 다음에도 028이 다시 실행된다.

특히 위험한 건 실패가 아니라 **조용한 되돌림**이다:

```sql
-- 028 (앞 파일)
CREATE OR REPLACE FUNCTION sync_role_id() ...  -- legacy role 컬럼 기반
CREATE TRIGGER trg_sync_role_id ...

-- 033 (뒤 파일)
DROP TRIGGER trg_sync_role_id ...
CREATE OR REPLACE FUNCTION guard_admin() ...   -- role_id 기반 재작성
ALTER TABLE auth_users DROP COLUMN role;
```

재실행하면 028의 `CREATE OR REPLACE FUNCTION`이 033의 구현을 **덮어쓴다**. 트리거만 가드하면 함수 본문이 옛 것으로 되돌아간 채 살아남는다.

## 해결

### 1. 앞 파일의 전제 의존 블록을 존재 검사로 감싼다

```sql
DO $$
BEGIN
  IF EXISTS (
    SELECT 1 FROM information_schema.columns
    WHERE table_name = 'auth_users' AND column_name = 'role'
  ) THEN
    EXECUTE $ddl$
      CREATE OR REPLACE FUNCTION sync_role_id() ... ;
      CREATE TRIGGER trg_sync_role_id ... ;
    $ddl$;
  END IF;
END $$;
```

- **트리거만이 아니라 함수까지** 감싼다 — 이게 실제로 놓치기 쉬운 지점이다
- 전제와 무관한 블록(테이블 생성·시드·신규 컬럼 추가)은 가드 밖에 그대로 둬 신규 설치를 보존한다
- 재실행 모델에서는 **이미 적용된 마이그레이션을 편집하는 것이 금기가 아니다** — 오히려 이 가드가 정상 절차다

### 2. 재실행 경로가 몇 개인지 센다

한 곳만 보고 판단하면 위험을 과소평가한다. 흔한 경로:

- CI 배포 잡 (브랜치 푸시마다)
- 패키지 `%post` / post-install 훅 (**설치뿐 아니라 업데이트마다**)
- 설치·초기화 CLI

가드가 없으면 로컬뿐 아니라 **CI 배포와 운영 서버 패키지 업데이트에서도 깨진다**.

### 3. 검증은 임시 DB 전량 적용으로

`sqlx::test` 같은 임시 DB에 001~N을 순서대로 전량 적용해 실제 DB 엔진에서 통과하는지 본다. 가드가 실제로 동작하는지는 **정적 확인만으로는 알 수 없다**.

### 기각한 대안

실행기를 "적용분 스킵"으로 바꾸는 것 — 기존 마이그레이션 전체의 멱등 전제와 부분실패 복구 동작이 **함께 바뀐다**. 파일 수가 많으면 회귀 범위가 감당되지 않는다.

## "전량 실행됐다"는 "정의대로 됐다"가 아니다

재실행 모델의 멱등 장치는 대부분 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`다.
이 구문은 **대상이 이미 있으면 아무 일도 하지 않는다** — 정의가 달라져도 맞춰주지 않는다.

그래서 **파일의 테이블 정의를 고쳐도 기존 DB에는 영원히 반영되지 않는다.** 실증 사례: 어떤 테이블에
기본키가 빠져 있었는데, 매 배포마다 마이그레이션 44개가 전부 실행되는데도 끝까지 안 고쳐졌다.
로그에는 44개 전량 성공이 찍힌다.

⚠️이게 위험한 이유는 **로그가 안심을 준다**는 데 있다. "전량 재실행되니 최신 정의가 반영되겠지"라는
직관이 정확히 반대다 — **전량 재실행되기 때문에 아무도 정의 변경을 의심하지 않는다.**

정의를 바꿔야 한다면 `ALTER`를 쓰는 새 파일을 추가해야 한다. 그리고 실제 스키마가 파일과 일치하는지
(**드리프트**) 주기적으로 확인해야 한다.

## 기준선(baseline) 통합의 전제

파일이 수십 개로 불어나면 **오늘의 스키마 스냅샷 하나로 접는 것**(기준선 통합)이 정리 수단이 된다.
이 작업의 전제와 성패 기준은 분명하다.

- 🔴**전제: 드리프트 0.** 실제 DB가 파일 정의와 어긋난 채로 스냅샷을 뜨면 **결함을 정본으로 굳힌다.**
  통합 전에 실제 스키마와 파일 적용 결과를 대조해 차이가 없음을 먼저 확인한다.
- **성패 기준: 동등성 증명.** 기준선 하나를 적용한 결과가 기존 N개를 적용한 결과와 **카탈로그 수준에서
  같아야 한다**(테이블·컬럼·타입·제약·인덱스·함수). 증명 전에는 기존 파일을 지우지 않는다.
- **참조처를 전수로 센다** — CI 잡, 패키지 설치 훅, 설치 CLI, 테스트 하네스. 특히 **파일을 빌드 시점에
  임베드하는 도구**는 같이 안 고치면 조용히 깨진다.
- 기존 DB에 도입할 땐 **기준선이 이미 적용된 것으로 표시**(baseline stamp)해야 한다. 표준 절차다.

기준선 통합과 **실행기 교체(한 번만 실행 + 체크섬 추적)는 별개 작업**이다. 한 번에 하면 실패 원인을
가릴 수 없다.

## 함께 걸리는 함정

- **적용 이력 테이블로 적용 상태를 판단하지 마라** — 기록과 실제 스키마가 어긋난다(표는 027인데 실제는 037인 상태가 실제로 생긴다)
- **실행 중인 구 프로세스 위에서 마이그레이션을 돌리지 마라** — 구 바이너리의 주 인증 경로가 삭제되는 컬럼을 읽으면 적용 순간부터 전면 마비다. `정지 → 마이그레이션 → 시작` 순서를 모든 경로가 지켜야 한다
- **요약 문서가 원문에 없는 규칙을 만들어낸다** — "한 번 배포된 마이그레이션은 수정 금지"처럼 이 모델과 **정반대 방향**의 규칙이 요약에 들어가면, 나중에 읽는 사람이 원문 대신 요약을 믿는다


## 뷰 열 수 충돌 — 두 번째 재실행부터 실패

전량 재실행 모델에서 실제로 자주 터지는 형태 하나가 **뷰**다.

앞 파일이 `CREATE OR REPLACE VIEW` 로 만든 뷰를, 뒤 파일이 **열을 늘려** 다시 정의했다고 하자.
001 부터 다시 도는 순간 앞 파일이 **열 수가 다른 뷰를 되돌리려다 멈춘다** —
`CREATE OR REPLACE VIEW` 는 기존 뷰의 **열을 제거하거나 순서를 바꾸는 재정의를 거부**하기 때문이다.

증상은 "첫 실행은 되는데 **두 번째 실행부터 실패**" 다. 개발 환경에서만 재현되고 신규 설치에서는 안 나므로
발견이 늦는다.

⇒ 앞 파일의 뷰 정의를 **`DROP VIEW IF EXISTS` 뒤에 생성**하도록 바꾸거나, 뒤 파일의 변경을 앞 파일에
합쳐 정의 지점을 하나로 만든다. 함수(`CREATE OR REPLACE FUNCTION`)에서 나는 되돌림 문제와 **같은 뿌리**다.
