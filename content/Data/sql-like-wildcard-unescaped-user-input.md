# LIKE 패턴에 사용자 입력을 그대로 넣으면 남의 행이 끌려온다

> **TL;DR**: `LIKE`에서 `_`는 한 글자, `%`는 임의 문자열을 뜻한다. 사용자가 정한 이름에 이 문자가 들어 있으면 **바인딩 파라미터를 써도** 의도하지 않은 행이 매칭된다. SQL 인젝션과는 다른 층위의 문제다.

## 증상

- 이름에 밑줄이 들어간 폴더(`team_a`)의 설정을 조회했더니 **다른 폴더(`teamXa`)의 설정이 딸려 나온다.**
- 접두사 검색이 이상하게 많은 결과를 낸다. 특히 이름에 `%`가 들어간 항목을 검색할 때.
- 대부분의 이름에서는 멀쩡하다 — **`_`나 `%`를 쓴 이름에서만** 틀린다. 그래서 재현이 들쭉날쭉하고 "가끔 이상하다"로 넘어가기 쉽다.

## 원인

하위 경로나 접두사를 찾을 때 흔히 이렇게 쓴다.

```sql
-- 파라미터 바인딩은 했지만
SELECT * FROM acl WHERE path LIKE $1 || '/%';
```

바인딩은 **SQL 문법 인젝션**을 막는다. 하지만 `LIKE`의 패턴 메타문자는 **값 안에서 해석되므로 바인딩으로 막히지 않는다.** `$1 = 'team_a'`이면 실제 패턴은 `team_a/%`이고, 여기서 `_`는 "아무 한 글자"라 `teamXa/...`도 매칭된다.

이 결함이 위험한 지점은 **권한·설정 조회**다. 남의 행이 끌려오면 **다른 대상의 권한 설정이 적용**될 수 있다. 조회 범위가 넓어지는 것이 곧 인가 오류가 된다.

⚠️ **역방향도 문제다** — 정확히 `_`를 포함한 이름을 찾으려는 검색이 원하지 않는 것까지 잡는다. 사용자에게는 "검색이 부정확하다"로만 보인다.

## 해결

**LIKE 패턴에 들어가는 값은 이스케이프한다.** 이스케이프 문자를 명시하고, 값 안의 `\`·`%`·`_`를 모두 앞에 붙여 escape한다.

```sql
-- PostgreSQL: ESCAPE 절로 이스케이프 문자를 명시
SELECT * FROM acl
WHERE path LIKE replace(replace(replace($1,'\','\\'),'%','\%'),'_','\_') || '/%'
      ESCAPE '\';
```

애플리케이션 쪽에서 값을 이스케이프한 뒤 넘기는 편이 읽기 쉽다. **치환 순서가 중요하다 — 백슬래시를 먼저 처리하지 않으면 뒤에 붙인 이스케이프를 다시 이스케이프한다.**

**더 나은 선택: LIKE를 안 쓴다.**

- 경로 접두사 매칭이 목적이라면 **경로를 세그먼트로 분해해 별도 컬럼/테이블로 두거나**, PostgreSQL의 `ltree` 같은 계층 타입을 쓴다. 의도가 스키마에 드러나고 인덱스도 정확히 걸린다.
- 완전 일치가 목적이면 `=`를 쓴다. "혹시 하위도"를 위해 LIKE를 쓰는 순간 이 함정에 들어간다.
- 접두사만 필요하면 `starts_with(path, $1)`(PostgreSQL 15+) 또는 범위 조건(`path >= $1 AND path < $1 || chr(255)`)으로 대체할 수 있다. 메타문자 해석이 아예 없다.

**검증**: 테스트 픽스처 이름에 `_`와 `%`를 **일부러 넣는다.** `team_a`, `100%_done` 같은 이름이 하나도 없으면 이 결함은 절대 안 잡힌다.
