# 마이그레이션을 기준선 하나로 압축할 때의 전제

> **TL;DR**: 마이그레이션 파일이 수십 개로 늘면 **기준선(baseline) 하나로 압축**하고 싶어진다. 성립 조건은 단 하나 — **모든 환경이 이미 압축 지점을 지났다는 것**. 하나라도 그 앞에 있으면 기준선은 스키마를 덮어쓰거나 적용 실패로 배포를 세운다. 그래서 압축보다 먼저 할 일은 **적용 진입점을 하나로 모으는 것**이다. 입구가 셋이면 전제를 확인할 자리도 셋이다.

---

## 용어

| 표기 | 원어 | 뜻 |
|---|---|---|
| 기준선 | baseline | 그 시점까지의 스키마 전체를 담은 단일 마이그레이션. 이후 파일만 순차 적용된다 |
| 압축 | squash | 여러 마이그레이션을 하나로 접는 작업 |
| 적용 이력 | migration history | 어떤 마이그레이션이 적용됐는지 DB에 기록해 두는 표 |
| 시드 | seed | 스키마와 별개로 넣는 초기 데이터 |

## 왜 압축하나

- 파일이 수십 개면 **로컬 초기화가 느리고**, CI가 매번 전부 재생한다.
- 오래된 파일일수록 지금은 존재하지 않는 컬럼·타입을 참조해 **읽어도 현재 스키마를 알 수 없다**.
- 압축본 하나는 "지금 스키마가 무엇인가"의 답이 된다.

## 전제 — 여기서 깨진다

압축이 안전한 것은 **압축 대상 구간을 모든 환경이 이미 적용했을 때**뿐이다.

```text
운영 A: 001..050 적용 완료  → 기준선 도입 OK (이력만 갈아끼움)
운영 B: 001..037 적용        → 038..050 이 사라졌으므로 영원히 못 따라잡는다
신규   : 아무것도 없음        → 기준선 하나만 적용하면 됨 OK
```

문제는 **환경 B의 존재를 압축 시점에 알기 어렵다**는 것이다. 배포 경로가 여럿이면 각각 다른 지점에 멈춰 있을 수 있고, 오래 안 켠 설치본은 확인할 방법조차 없다.

## 해결 — 순서를 뒤집는다

1. **적용 진입점을 하나로 모은다.** 배포 스크립트·설치 도구·로컬 개발이 각자 마이그레이션을 돌리고 있다면, 전부 같은 명령을 부르게 바꾼다. 이 단계에서 "누가 어디까지 적용했는지"를 물어볼 자리가 생긴다.
2. **진입점이 하나로 남는지 계약 시험으로 잠근다.** 그러지 않으면 다음 사람이 네 번째 경로를 만든다.
3. 그다음 압축한다. 기준선 생성은 **자동 생성기**로 만들고 손으로 쓰지 않는다 — 손으로 쓴 스키마는 조용히 썩는다([[handwritten-schema-fixture-rot]]).
4. 시드 데이터는 기준선과 **별개 정본**으로 둔다. 스키마와 데이터를 한 파일에 섞으면 다시 압축할 수 없다.

```bash
# 진입점 통합 전: 경로마다 제각각
./deploy.sh          # psql -f migrations/*.sql
./install.sh         # 자체 루프
make dev-db          # 또 다른 순서

# 통합 후: 전부 이걸 부른다
myapp-config migrate
```

## 압축 후에 남는 함정

- **권한**: root로 도는 설치 경로와 서비스 계정으로 도는 배포 경로가 서로 다른 DB 사용자를 쓰면, 한쪽만 적용에 실패한다. 진입점을 통합했다면 권한 문제도 한 곳에서 드러난다.
- **배포 트리거**: 마이그레이션 파일만 바뀐 커밋에서 설치 도구가 다시 배포되지 않으면, 새 기준선을 아는 코드가 현장에 없다. CI 규칙의 변경 감지 경로에 마이그레이션 디렉터리를 넣어야 한다.
- **접속 대상**: CI의 스키마 적용 잡이 접속 대상을 환경 변수 기본값에 맡기면, 의도하지 않은 DB에 기준선을 적용한다. 대상을 명시로 못박는다.
