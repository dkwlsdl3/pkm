# 부하 중 클라이언트 축출 — 유휴 클라이언트도 끊긴다

> **TL;DR**: 클라이언트가 **축출(eviction)** 되어 I/O 오류로 중단된다. 쓰기 방식(버퍼/동기)이나 stripe 설정과 무관하다. 부하가 원인처럼 보이지만, 실제 원인은 **클라이언트 쪽 방화벽이 LNET 포트를 막아 서버→클라이언트 역방향 연결이 안 되는 것**이었다. 락 콜백을 전달할 길이 없으니 서버가 클라이언트를 끊는다. **한 방향만 열려도 마운트는 된다** — 그래서 연결 점검을 통과한다.

---

## 용어

| 표기 | 원어 | 뜻 |
|---|---|---|
| 축출 | eviction | 서버가 클라이언트의 연결·락을 강제로 끊는 것. 클라이언트 쪽에서는 진행 중이던 I/O가 오류로 끝난다 |
| EIO | Input/Output error | 입출력 오류. 축출된 클라이언트의 쓰기가 이 오류로 중단된다 |
| 락 콜백 | lock callback | 서버가 클라이언트에게 "쥐고 있는 락을 반납하라"고 요청하는 것 |

## 증상

클라이언트 3대가 각각 10GB 파일을 동시에 쓰면 **7회 중 4회에서 한 대가 EIO로 중단**된다.

- 완주하지 못하므로 **그 회차의 대역폭 값은 존재하지 않는다**
- 버퍼 쓰기(10건)와 동기 쓰기(7건) **양쪽에서 발생** — 쓰기 방식을 바꿔 피할 수 없다
- stripe 설정과 무관하다

### 부하 주체별로 갈라 보면 더 나쁘다

축출 타임라인을 **부하 주체별 구간으로 나누어** 보면, 서버(호스트) 단독으로 도는 측정 구간에서도 축출이 늘어난다. 그 45분 동안 클라이언트는 **마운트만 되어 있고 아무 일도 하지 않았는데 9건**이 늘었다.

> "클라이언트가 무리하게 쓰면 끊긴다"보다 나쁜 그림이다 — **서버가 바쁘면 유휴 클라이언트도 끊긴다.**

## 원인 — 클라이언트 방화벽이 역방향 연결을 막는다

축출은 서버가 클라이언트의 **락 콜백 응답을 제한 시간 안에 받지 못할 때** 일어난다. 응답이 늦은 것이 아니라 **요구가 도달하지 못한 것**이 실제 원인이었다.

```
클라이언트 → 서버   마운트·읽기·쓰기가 나가는 방향. 열려 있다 ✅
서버 → 클라이언트   락 반납 요구(콜백)가 나가는 방향. 방화벽이 막았다 ❌
```

🔴 **핵심은 "한 방향만 열려도 마운트가 된다"는 것이다.** 클라이언트에서 거는 연결만으로 마운트·읽기·쓰기가 다 되므로, 연결 점검을 해도 통과한다. 서버가 락을 회수하려는 순간에야 드러난다.

부하는 원인이 아니라 **드러나는 조건**이었다. 부하가 클수록 서버가 락을 회수할 일이 잦아지므로 축출이 늘어 보인다.

### 부하 가설이 뒤집힌 근거

- **1대·유휴·회선을 세운 상태에서도 재현된다** → 다중 클라이언트 부하는 필요조건이 아니다
- 버퍼 쓰기와 동기 쓰기 **양쪽에서 발생**한다 → 쓰기 방식으로 피할 수 없다
- 장치가 **1개인 구성에서도 같은 실패**가 난다 → 분산 설정과 무관하다

### 확정 후 대조

방화벽을 연 뒤 같은 조건을 전수 재측정했다 — **실패율 59% → 18회 연속 0건.**

## 관측 한계 (원인 추적을 어렵게 하는 것들)

- **축출 사유는 기본 로그에 안 나온다.** 디버그 채널을 켜야 사유가 보인다
- **커널 로그의 시각이 실제 사건 시각과 어긋난다.** 타임라인을 다른 계측과 맞출 때 이 지연을 감안해야 한다
- 커널 링 버퍼가 넘치면 **축출 건수가 줄어든다** — 사건이 아니라 기록이 사라지는 것이라 값만 보면 개선으로 읽힌다 → [[kernel-ring-buffer-overflow-counting]]

⚠️ 두 달간 못 찾은 이유는 관측이 어려워서만이 아니다. **자체 관측만으로 파고들었고 외부 사례 검색이 늦었다.** 알려진 현상이었다.

## 측정·보고 시 지켜야 할 것

- **축출 건수는 측정 창과 함께 적는다.** 창 없는 누적 건수는 인용할 수 없다 — 같은 문서에 "47분 18건"과 "70분 25건"이 병존하면 어느 것도 쓸 수 없다
- **완주 실패가 속도보다 먼저다.** 부풀림 없이 전 클라이언트가 완주한 회차가 0회라면, 그 조건의 답은 "몇 MB/s"가 아니라 **"측정 불가"** 다
- 측정 불가라는 사실 자체가 결과다. 고객 문의가 정확히 그 조건이라면 더욱 그렇다

## 확인

```bash
# 축출 카운터 (서버 측)
lctl get_param -n obdfilter.*.eviction_count
lctl get_param -n mdt.*.eviction_count

# 커널 로그에서 축출 시각 확인
dmesg -T | grep -i evict

# 🔴 역방향 연결 확인 — 서버에서 클라이언트로 LNET 포트가 열려 있는가
#    (클라이언트에서 서버로만 확인하면 이 문제는 안 잡힌다)
lctl ping <CLIENT_NID>          # 서버에서 실행
ss -tnp | grep <LNET_PORT>      # 클라이언트에서 역방향 세션 존재 확인

# 클라이언트 방화벽이 LNET 포트를 막고 있지 않은지
firewall-cmd --list-all         # 또는 iptables -L -n / ufw status
```

## 예방

- 클라이언트를 새로 붙일 때 **양방향으로 점검한다.** 마운트 성공은 한 방향만 증명한다
- 구축 절차의 연결 점검 항목에 `서버 → 클라이언트` 방향을 명시적으로 넣는다 — 단일 노드 구성으로 개발하면 이 방향이 자연히 빠진다
