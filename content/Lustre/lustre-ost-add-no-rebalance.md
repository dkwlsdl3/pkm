# OST 를 추가해도 기존 데이터는 재배치되지 않는다

> **TL;DR**: Lustre 에 OST 를 붙이면 **그 시점 이후 새로 만들어지는 파일**만 새 OST 로 배분된다. 기존 파일은 그대로 있다 — 자동 리밸런싱은 **없는 기능**이다. 그래서 "증설이 느린 이유는 데이터 재배치"라는 설명은 사실이 아니다(실제 소요는 **타겟 포맷** 시간이다). 균형이 필요하면 `lfs migrate` 로 직접 옮겨야 한다.

## 개요

- **무엇**: OST 추가 시 Lustre 의 실제 동작 — 신규 할당만 바뀌고 기존 오브젝트는 이동하지 않는다.
- **왜 / 언제**: 용량 증설 설계·시연 설명·증설 소요 시간 산정. **잘못 설명하면 "몇 시간 걸린다"는 근거 없는
  수치가 발표 자료에 들어간다.**

## 동작 / 예시

새 OST 를 붙이면 MDS 의 오브젝트 할당기가 그 OST 를 후보에 넣는다. **이미 스트라이프가 정해진 파일은
건드리지 않는다** — 파일의 레이아웃(어느 OST 에 몇 조각)은 생성 시점에 확정되기 때문이다.

```bash
lfs df -h                      # OST 별 사용률 — 새 OST 만 비어 있다
lfs osts                       # 활성 OST 목록
lfs getstripe <파일>            # 이 파일이 어느 OST 를 쓰는지 (추가 후에도 그대로)
```

**증설 소요 시간의 실체는 타겟 포맷이다.** 재배치가 아니다.

| 단계 | 하는 일 |
|---|---|
| 블록 장치 생성 | zvol·LV 생성 (빠름) |
| 노드에 부착 | 가상 디스크 연결 (빠름) |
| **러스터 타겟 포맷** | `mkfs.lustre` — **여기가 대부분의 시간**. 실측 예: 113GB 에 93초 |
| 마운트·등록 | MGS 에 등록 후 즉시 활성 |

기존 데이터를 옮기고 싶으면 명시적으로 해야 한다.

```bash
# 특정 OST 에서 빼내며 재배치
lfs find /mnt/store --ost <OST_IDX> | \
  while read -r f; do lfs migrate -c 1 "$f"; done

# 새 기본 스트라이프를 디렉터리에 지정 (이후 생성 파일에만 적용)
lfs setstripe -c 4 /mnt/store/newdata
```

## 주의

> [!WARNING]
> **증설 마법사가 풀 분산을 안내하지 않으면 같은 백엔드 풀에 OST 가 쌓인다.** 그 상태에서 재배치를 돌리면
> **같은 디스크 안에서의 왕복**이라 성능 이득이 없다. 따라서 우선순위는 ①증설 시 풀 분산 안내 ②OST 간
> 사용률 편차 경고 ③그 다음이 재배치다. 순서를 뒤집으면 만든 기능이 쓸모가 없다.

> [!WARNING]
> `lfs migrate` 는 **파일을 읽고 다시 쓴다.** 운영 중 대량 실행은 I/O 를 그대로 잡아먹고, 진행 중 파일이
> 열려 있으면 실패한다. 창을 잡고 배치로 돌리며 진행률·실패 목록을 남겨라.

> [!NOTE]
> "자동 재배치(auto-rebalancing)"를 요구받으면 **없는 기능을 켜는 것이 아니라 만들어야 하는 기능**임을
> 먼저 밝혀라. 공수 산정이 완전히 달라진다.

> [!NOTE]
> 소형 파일 성능이 화제라면 **DoM(Data-on-MDT)** 적용 여부를 먼저 확인하라 — 작은 파일 본문을 MDT 에 두어
> OST 왕복을 없애는 기능인데, 기본으로 켜져 있지 않아 "약점"으로만 알려진 경우가 많다.
> ```bash
> lfs getstripe -v <작은파일>   # layout 에 mdt 컴포넌트가 있는지
> ```
