# 연결 상한과 총 상한은 따로 건다

> **TL;DR**: HTTP 클라이언트의 총 상한(전체 데드라인)만 걸면, **상대가 죽어 TCP 연결조차 못 맺는 경우에도 총 상한을 통째로 기다린다.** 긴 작업 때문에 총 상한을 크게 잡을수록 죽은 상대를 기다리는 시간이 그만큼 늘어난다. 연결 상한을 짧게 따로 걸면 그 대기를 몇 초에 끊고, 동시에 **"시작도 못 했다" 와 "돌고 있을 수 있다" 를 가를 수 있다.**

---

## 증상

노드 하나가 정지했는데, 그 노드를 부르는 요청이 **5분(총 상한)을 꽉 채우고** 실패했다.
긴 작업을 위해 총 상한을 60초 → 300초로 올린 변경이, 죽은 상대를 기다리는 시간도 5배로 늘렸다.

## 원인

대부분의 HTTP 클라이언트에서 "timeout" 은 **연결 수립부터 응답 수신 완료까지 전체 데드라인**이다.
연결 단계가 이 안에 포함되므로, 별도 상한이 없으면 연결 시도도 전체 데드라인까지 매달린다.

```rust
// 총 상한만 — 죽은 상대에게도 300초를 쓴다
reqwest::Client::builder().timeout(Duration::from_secs(300)).build()?
```

## 해결

```rust
reqwest::Client::builder()
    .timeout(NODE_LONG_OP_TIMEOUT)        // 총 데드라인 (작업 길이 기준)
    .connect_timeout(Duration::from_secs(5))  // 연결 상한 (경로 상태 기준)
    .build()?
```

**두 상한은 근거가 다르다.**

| 상한 | 무엇을 재는가 | 값의 근거 |
|---|---|---|
| 연결 상한 | 상대에 닿을 수 있는가 | 네트워크 왕복 시간. 같은 호스트의 브리지 네트워크면 밀리초 단위 → 수 초면 충분 |
| 총 상한 | 작업이 얼마나 걸리는가 | 가장 느린 정상 작업의 소요 시간 |

값이 다른 것보다 **사후 처리가 다른 것이 더 중요하다.**

- **연결 실패** = 명령이 **시작되지도 않았다.** 확정 실패이고 **재시도가 안전하다.**
- **총 상한 초과** = 상대에서 **돌고 있을 수 있다.** 실패가 아니라 미지이고, 재시도하면 같은
  작업이 두 번 실행된다 → [[timeout-is-unknown-not-failure]]

## 주의

> [!WARNING]
> **연결 상한을 크게 잡으면 의미가 없다.** 총 상한과 구분이 사라져 위 두 경우가 다시 섞인다.
> 연결 상한은 "혼잡을 견딜 만큼 짧게" 잡는 값이지, 여유를 주는 값이 아니다.

> [!WARNING]
> **방화벽 DROP 은 연결 상한으로만 끊긴다.** REJECT 는 즉시 `ECONNREFUSED` 로 돌아오지만
> DROP 은 아무 응답이 없어 상한이 유일한 탈출구다.
