# 리버스 프록시 응답 대기 시간과 긴 다운로드의 간헐 504

> **TL;DR**: 큰 폴더를 묶어 내려받을 때만 **간헐적으로 504 Gateway Timeout**(게이트웨이 시간 초과 — 프록시가 뒤쪽 서버 응답을 기다리다 포기했다는 뜻)이 난다면, 애플리케이션이 아니라 앞단 리버스 프록시의 **응답 대기 기본값(nginx 기준 60초)** 을 먼저 의심한다. 긴 응답을 내는 창구만 골라 값을 늘리고, 그 설정이 나중에 되돌아가지 않도록 **검사로 고정**한다.

## 증상

- 작은 폴더는 잘 받아지는데 **큰 폴더에서만** 다운로드가 끊긴다. 실패 시각이 늘 비슷하다(예: 요청 후 약 60초)
- 애플리케이션 로그에는 **오류가 없다**. 서버는 계속 응답을 쓰고 있었고, 끊은 쪽은 프록시다
- 브라우저에는 504가 뜨거나 파일이 잘린 채 저장된다
- 같은 요청을 다시 하면 성공하기도 한다 — 서버 부하·디스크 속도에 따라 임계 시간을 넘길 때만 터지므로 **재현이 들쭉날쭉**하다

## 원인

nginx의 `proxy_read_timeout` 기본값은 **60초**다. 이 값은 전체 전송 시간이 아니라 **연속된 두 읽기 사이의 간격** 상한이다. 그래서 이런 구조가 걸린다.

```text
클라이언트 ──> nginx ──> 앱 서버
                 │        └ 폴더를 훑고 압축을 준비하는 동안 아무 바이트도 안 보냄
                 └ 60초 동안 읽을 게 없으면 504로 끊는다
```

핵심은 **"응답을 시작하기까지 걸리는 시간"** 이다. 폴더 전체를 먼저 훑어 목록·용량을 계산하거나 임시 파일에 다 담은 뒤에 스트리밍을 시작하는 구현이면, 그 준비 구간 내내 프록시로 나가는 바이트가 0이다. 파일이 커질수록 준비 구간이 길어지고, 어느 순간 60초를 넘긴다.

⚠️ 다운로드 총 시간이 60초를 넘는 것은 문제가 아니다. **바이트가 흐르는 동안에는 타이머가 계속 갱신**되기 때문이다. 그래서 "느린 회선에서는 되고 큰 폴더에서는 안 되는" 혼란스러운 양상이 나온다.

## 해결

### 1. 긴 응답을 내는 창구만 골라 값을 올린다

전역으로 올리면 진짜로 멈춘 백엔드까지 오래 붙잡고 있게 된다. 경로 단위로 좁힌다.

```nginx
location /api/(다운로드 계열 경로) {
    proxy_pass http://app;
    proxy_read_timeout 600s;     # 준비 구간이 긴 창구에만
    proxy_buffering off;         # 버퍼에 다 모으지 말고 즉시 흘려보낸다
}
```

`proxy_buffering off`가 함께 필요한 경우가 많다. 버퍼링이 켜져 있으면 nginx가 응답을 모아뒀다 보내면서 클라이언트 쪽 체감 지연이 더 커진다.

### 2. 준비 구간 자체를 줄인다 (근본 대책)

- **스트리밍 압축**으로 바꿔 첫 바이트를 빨리 내보낸다. 바이트가 흐르기 시작하면 타이머 문제는 사라진다
- 사전 훑기에 **용량 상한과 항목 수 상한을 둘 다** 건다. 용량만 제한하면 작은 파일 수십만 개짜리 폴더에서 훑기 자체가 오래 걸린다
- 정말 오래 걸리는 작업이면 동기 응답을 포기하고 **비동기 작업 + 완료 후 내려받기**로 바꾼다

### 3. 설정이 되돌아가지 않도록 검사로 고정한다

이 부류의 값은 배포 설정을 손대는 과정에서 **조용히 기본값으로 돌아간다**. 그리고 되돌아간 사실은 큰 폴더를 받아보기 전까지 아무도 모른다. 그래서 수정보다 **drift 검사**(설정이 의도에서 벗어났는지 확인하는 검사)가 중요하다.

- 긴 응답을 내는 경로 목록을 코드/설정 어딘가에 명시해두고, 그 경로들이 프록시 설정에서 상한을 부여받았는지 자동 검사한다
- 새 다운로드 창구를 추가했을 때 목록에 없으면 실패하게 만들면, **다음 사람이 같은 함정에 안 빠진다**

## 확인 방법

```bash
# 응답의 첫 바이트까지 걸린 시간과 전체 시간을 나눠 본다
curl -o /dev/null -s -w 'ttfb=%{time_starttransfer}s total=%{time_total}s code=%{http_code}\n' \
  '<다운로드 URL>'

# ttfb 가 60초 근처에서 code=504 면 준비 구간이 원인이다
```
