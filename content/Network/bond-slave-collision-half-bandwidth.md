# 본딩 슬레이브 충돌 — 두 클라이언트가 회선을 절반씩 나눠 쓴다

> **TL;DR**: 본딩(bonding, 여러 물리 NIC를 하나로 묶는 것)은 **연결 단위로 슬레이브를 고른다.** 두 클라이언트가 같은 슬레이브에 배정되면 각자 그 물리 회선의 절반만 쓴다. 평균값으로 보면 "성능이 들쭉날쭉"으로 보이지만, **호스트별로 갈라 보면 두 상태로 깔끔하게 나뉜다.**

---

## 증상

클라이언트 3대의 대용량 순차 읽기를 반복 측정했더니 **CV(Coefficient of Variation, 변동계수 = 표준편차/평균)가 24%** 로 나왔다. 반복이 부족한 것으로 보였다.

## 판별 — 평균이 아니라 원시를 호스트별로 갈라 본다

원시 값을 호스트별·회차별로 늘어놓으면 **두 덩어리**로 갈리고, **각 덩어리 안에서는 편차가 거의 0**이다.

| 상태 | 값 | 회선 대비 | 덩어리 내 편차 |
|---|---|---|---|
| 3대가 각자 회선을 온전히 사용 (2회) | 331.9 MiB/s | **98%** | 0.03% |
| 두 대가 하나를 나눠 사용 (3회) | 223.2 MiB/s | 66% | 0.04% |
| (둘의 평균) | 259.5 | 77% | — |

평균 259.5는 **어느 상태도 아닌 값**이다. 그래서 반복을 늘려도 편차가 줄지 않는다 — 두 모집단을 하나로 섞고 있기 때문이다.

갈라 놓으면 결론이 확정된다: **대용량 순차 읽기는 회선이 막는다(98%).**

## 원인 확인 — 산술이 맞아야 한다

가설을 세웠으면 **숫자로 검산**한다.

```
1 Gbps 를 두 클라이언트가 나눔      → 500 Mbps
실측 TCP 효율 94% 적용             → 56.0 MiB/s
실측값                              → 56.1 ~ 56.4 MiB/s   ← 일치
```

경쟁 가설(저장 타깃 충돌)은 산술이 맞지 않아 기각했다 — 타깃 하나가 단독으로 234 MiB/s를 내므로 둘이 공유해도 112까지 떨어질 이유가 없다.

## 왜 생기는가

본딩의 부하 분산은 **패킷 단위가 아니라 연결(또는 MAC/IP) 단위 해시**다(`xmit_hash_policy`). 클라이언트 수가 적으면 해시가 고르게 퍼지지 않아 **두 클라이언트가 같은 슬레이브에 앉는 일이 흔하다.**

- 클라이언트 수가 슬레이브 수보다 훨씬 많아야 통계적으로 고르게 퍼진다
- 즉 본딩은 **한 연결의 속도를 올려 주지 않는다.** 총량은 늘지만 개별 연결은 슬레이브 하나의 상한을 넘지 못한다

## 대응

- 측정 시 **호스트별 원시값을 반드시 남긴다.** 합계·평균만 남기면 이 현상이 보이지 않는다
- 해시 정책(`xmit_hash_policy layer3+4` 등)을 확인한다 — 다만 정책을 바꿔도 **연결 단위라는 성질 자체는 남는다**
- ⚠️본딩 "효과"를 측정하려고 본딩을 끄는 대조군은 신중히 — 스위치 설정을 함께 바꿔야 하면 검증된 구성을 잃는다

```bash
cat /proc/net/bonding/bond0        # 슬레이브 상태·해시 정책
ip -s link show <slave>            # 슬레이브별 실제 트래픽 확인
```
