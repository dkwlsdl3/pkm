# 취소가 이미 확정된 성공·실패를 덮어쓰면 안 된다

> **TL;DR**: 여러 조각으로 나뉜 작업(청크 업로드·배치 처리)에서 사용자가 취소를 누르면, **"취소됨"이 앞서 확정된 조각별 성공·실패를 전부 덮어쓰는** 구현이 나온다. 이미 서버에 올라간 파일은 올라간 것이고, 이미 난 오류는 난 것이다. 취소는 **앞으로 보낼 것**만 막아야 한다.

## 증상

- 20개 중 12개가 올라간 뒤 취소했는데 "업로드가 취소되었습니다"만 뜨고, 어느 것이 올라갔는지 알 수 없다.
- 취소 전에 확정된 청크 실패 사유가 취소 정리 과정에서 사라진다.
- 취소 뒤에 도착한 오류가 "취소됨"에 묻혀 사용자에게 보고되지 않는다.
- 반대로 취소 중에 완료된 조각이 성공으로 보고돼 취소가 안 먹은 것처럼 보인다.
- **취소 정리가 끝난 뒤 병렬 청크가 깨어나 다시 전송된다.**

## 원인

취소를 **결과 판정보다 우선하는 단일 플래그**로 두면 이렇게 된다.

```text
if (cancelled) return { status: 'cancelled' };   // ← 앞서 쌓인 결과를 버린다
return aggregate(results);
```

그리고 취소 상태를 **컴포넌트나 전역**에 두면, 정리가 끝나 플래그가 초기화된 뒤에도
아직 대기 중이던 갈래(재시도 백오프, 병렬 청크)가 깨어나 자기 요청을 계속 보낸다.

## 해결

- 조각별 결과를 **확정 즉시 기록**하고, 취소는 그 기록 위에 **추가 정보**로만 얹는다 — "12개 성공 · 3개 실패 · 5개 취소로 미전송".
- 취소 상태를 **실행(run) 단위 객체에 묶는다.** 전역/컴포넌트 플래그를 쓰면 정리 후 깨어난 갈래가 새 실행으로 오인한다.
- 재시도 **대기 중에도** 취소 신호를 확인한다. 백오프 타이머가 깨어난 뒤 조건을 보면 이미 요청이 나간 뒤다.
- 취소 이후에 도착한 오류는 **취소와 별개로** 보고한다. 묻으면 데이터 불일치의 원인을 영영 못 찾는다.

```text
// 취소가 결과를 덮지 않는 형태
결과 = 조각별_확정결과.집계()
결과.미전송 = 취소로_보내지_않은_조각들
표시(결과)   // 성공·실패·미전송이 모두 남는다
```

시험은 **병렬 청크의 실패 시각을 어긋내** 취소와 경쟁시켜야 재현된다. 순차 실행으로는 안 잡힌다.
