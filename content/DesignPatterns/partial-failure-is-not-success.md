# 부분 실패는 성공이 아니다

> **TL;DR**: 여러 항목을 처리하는 작업이 일부를 못 처리하고도 성공을 답하면, **그 답을 믿은 다음 단계가 원본을 지운다.** 복사·이전·업로드·롤백처럼 뒤에 파괴적 단계가 붙는 작업일수록 부분 실패를 반드시 위로 전파해야 한다.

## 증상

- 이동이 "완료" 라고 답했는데 목적지에 **일부 항목이 없다**. 원본은 이미 지워졌다
- 업로드가 성공인데 파일이 **잘려 있다**
- 롤백 로그에 "되돌렸음" 이 찍혔는데 실제로는 안 돌아갔다
- 감사 기록에 실패한 흔적이 **아예 없다** — 성공만 기록됐기 때문이다

## 원인

반복문 안에서 항목별 오류를 삼키는 관용구가 원인이다.

```rust
for item in items {
    let _ = copy_one(item).await;      // 오류를 버린다
}
Ok(())                                  // 전체는 성공
// 호출자: 성공을 받았으니 원본을 지운다
remove_source(&src).await?;
```

같은 형태가 여러 언어에서 반복된다 — `except: pass`, `.catch(() => {})`, `if err != nil { }`.

**핵심은 "일부 실패" 를 표현할 값이 반환 타입에 없다는 것이다.** 성공/실패 두 값만 있으면 코드는
반드시 부분 실패를 둘 중 하나로 거짓 보고한다.

## 해결

**하나 — 반환 타입에 부분 실패를 넣는다.** 처리한 것과 못 한 것을 함께 돌려준다.

```rust
struct BatchOutcome { succeeded: Vec<Id>, failed: Vec<(Id, Error)> }
// 호출자는 failed 가 비어 있을 때만 파괴 단계로 넘어간다
```

**둘 — 파괴적 단계 앞에 확인을 붙인다.** "성공 응답을 받았다" 가 아니라 **"목적지에 전부 있다"** 를 근거로
원본을 지운다.

**셋 — 실패를 응답과 감사 기록 양쪽에 싣는다.** 화면에서 보이지 않으면 사용자는 성공으로 읽는다.

> [!WARNING]
> 되돌릴 수 없는 지점(파일 삭제, 외부 시스템 커밋)을 지난 뒤의 실패는 특히 위험하다. 여기서 오류를
> 버리면 시스템은 **일관성이 깨진 채로 성공을 보고**한다.
