# 관측 가능한 변화가 없는 변경은 확인에 실패해 원복된다

> **TL;DR**: 위험한 설정 변경에 "적용 → 확인 → 실패 시 자동 원복" 절차를 두면, 확인 단계를 **"무엇이 바뀌었는가"** 로 구현하기 쉽다. 그러면 바뀔 것이 없는 정당한 변경(같은 값 재적용, 관측 지표가 없는 항목)이 **영원히 확인에 실패해 반드시 원복된다.** 확인은 변화가 아니라 **요청한 목표 상태에 도달했는가**로 판정해야 한다.

## 용어

| 표기 | 원어 | 뜻 |
|---|---|---|
| 자동 원복 | auto-rollback | 적용 후 확인이 안 되면 이전 설정으로 되돌리는 안전장치. 원격 장비 설정 변경의 표준 패턴 |
| no-op 변경 | — | 적용은 정당하지만 관측 가능한 변화를 만들지 않는 변경 |
| 목표 상태 | desired state | 요청이 도달하려는 상태. 변화량이 아니라 결과값 |

## 증상

- 특정 항목만 적용이 매번 실패하고 자동 원복된다. 장비 쪽 로그에는 **적용이 성공했다고** 찍힌다.
- 같은 값을 다시 적용하는 요청도 실패한다("이미 그 값"이라 변화가 없다).
- 실패 이유가 "확인 불가"로만 남아 있어 무엇을 못 봤는지 알 수 없다.

## 원인

원격 설정 변경의 확인은 보통 **연결이 살아 있는지**로 대신한다. 주소를 바꾸는 변경이면 "새 주소로 접속되는가"가 곧 확인이 된다. 그래서 확인 로직이 **주소 변화**에 묶인다.

그런데 같은 절차를 주소를 건드리지 않는 항목에 쓰면 — MTU, 큐 길이, 옵션 토글 — 확인할 변화가 없다. 확인 함수는 "변화를 못 봤다 = 적용 실패"로 읽고 원복을 건다. **적용은 매번 성공하고 확인은 매번 실패하는** 고리가 된다.

## 해결

```text
1) 확인의 정의를 바꾼다
   변화 관측  →  목표 상태 도달 여부
   "주소가 바뀌었나" 대신 "지금 상태가 요청한 상태와 같은가"를 읽는다
   → no-op 변경은 즉시 확인 성공(이미 목표 상태)

2) 항목마다 확인 수단을 선언한다
   설정 항목 정의에 "이 항목은 무엇을 읽어 확인하는가"를 함께 둔다
   확인 수단이 없는 항목은 위험 등급을 낮추고 자동 원복 대상에서 뺀다

3) 사람이 확정할 통로를 둔다
   기계가 확인할 수 없는 항목(원리상 왕복 불가)은 화면에서 사람이 확인해
   확정하게 한다. 확인 못 함을 실패로 접지 않는다
```

> [!WARNING]
> **"확인할 수 없음"을 "실패"로 접는 것이 근본 원인이다.** 미확정은 실패가 아니다 → [[timeout-is-unknown-not-failure]]. 미확정일 때 자동으로 되돌릴지 사람에게 물을지는 **항목별 위험도**로 정한다.

> [!WARNING]
> 되돌림이 항상 안전하다고 가정하지 마라. 원복 중에 다시 요청이 들어오거나 원복 자체가 실패하면 **아무도 몰지 않는 중간 상태**가 남는다. 되돌림 진행 상태도 원장에 남겨야 한다.
