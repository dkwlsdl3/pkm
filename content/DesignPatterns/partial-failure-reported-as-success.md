# 부분 실패를 완료로 보고하는 다단계 작업

> **TL;DR**: 여러 하위 단계로 이뤄진 작업에서 **일부만 실패**하면, 마지막 단계가 성공했거나 예외가 안 났다는 이유로 전체가 "완료"로 보고된다. 정직하게 보고하려면 **응답에 단계별 결과를 싣는 것**과 **화면이 그 결과를 표시하는 것**을 둘 다 고쳐야 한다. 한쪽만 고치면 사용자에게는 여전히 성공으로 보인다.

## 증상

- 계정 생성·프로비저닝처럼 단계가 여럿인 작업이 **항상 성공으로 뜬다**. 그런데 나중에 확인하면 홈 디렉터리가 없거나 쿼터가 안 걸려 있다
- 여러 건을 한 번에 처리하는 대량 등록에서 **일부가 조용히 빠진다**. 화면에는 "N건 등록 완료"만 뜬다
- 동기화 작업 집계에 **실패 건이 성공으로 계산**돼, 성공률이 늘 100%다
- 실패한 사용자에게도 **성공 전제의 안내 메일**이 나간다(존재하지 않는 경로를 알려주는 식)

## 원인

### 1. 응답 형태가 부분 실패를 표현하지 못한다

```rust
// 나쁜 예 — 성공/실패 두 값밖에 없다
async fn provision_user(...) -> Result<(), Error> {
    create_posix_account(...).await?;
    let _ = create_home_dir(...).await;   // 실패해도 넘어간다
    let _ = apply_quota(...).await;       // 여기도
    Ok(())                                 // → 호출자에겐 완전 성공으로 보인다
}
```

`let _ =`, `.ok()`, `if let Ok(..)`처럼 결과를 버리는 표현이 붙은 자리가 **부분 실패가 사라지는 지점**이다. 하위 단계를 계속 진행시키려는 의도(중간에 멈추면 더 나쁜 반쪽 상태가 된다) 자체는 맞지만, **진행과 보고를 같이 포기한 것**이 문제다.

### 2. 응답은 고쳤는데 화면이 버린다

백엔드가 `{ created: 8, failed: [{id, step, reason}] }`처럼 정직하게 돌려줘도, 화면이 `res.created`만 읽고 토스트를 띄우면 사용자 경험은 이전과 **완전히 동일하다**. 백엔드만 고치고 "해결"로 판정하기 쉬운 지점이라 특히 잘 남는다.

### 3. 집계가 실패를 성공으로 센다

배치 동기화에서 `for` 루프 안의 실패를 세지 않거나, 예외를 잡고 `continue`만 하면 **처리 건수 = 성공 건수**가 되어 성공률이 항상 100%가 된다.

## 해결

**단계별 결과를 값으로 만든다.** 성공/실패 2값이 아니라 단계마다 결과를 모은다.

```rust
struct StepOutcome { step: &'static str, ok: bool, reason: Option<String> }

async fn provision_user(...) -> ProvisionReport {
    let mut steps = Vec::new();
    steps.push(run_step("posix_account", create_posix_account(...)).await);
    steps.push(run_step("home_dir",      create_home_dir(...)).await);
    steps.push(run_step("quota",         apply_quota(...)).await);
    ProvisionReport { partial: steps.iter().any(|s| !s.ok), steps }
}
```

체크리스트:

1. **하위 단계를 계속 진행할지**와 **실패를 보고할지**를 분리한다. 진행은 계속하되 기록은 남긴다
2. 응답 스키마에 `partial`(또는 실패 목록)을 넣는다. 있으면 화면이 무시하기 어려워진다
3. **화면 코드를 같이 고친다.** 실패 항목을 목록으로 보여주고, 부분 실패를 성공 색으로 칠하지 않는다
4. **후속 액션의 조건도 다시 본다** — 안내 메일·다음 단계 트리거는 "요청이 접수됨"이 아니라 "그 단계가 실제로 성공함"을 조건으로 건다
5. 집계는 **시도·성공·실패를 각각** 센다. `처리 = 성공`으로 두지 않는다
6. 테스트는 **중간 단계만 실패**하는 경로를 반드시 포함한다. 전부 성공/전부 실패만 검증하면 이 결함은 절대 안 잡힌다

## 🔴 부분 실패 뒤에 파괴적 단계가 붙는 경우

보고만 어긋나는 것이 아니라 **데이터가 사라지는** 갈래가 따로 있다. 복사·이전·업로드처럼 뒤에
**원본 삭제**가 따라붙는 작업이다.

```rust
for item in items {
    let _ = copy_one(item).await;   // 항목 오류를 삼킨다
}
Ok(())                               // 전체는 성공
// 호출자는 성공을 받았으니 원본을 지운다
remove_source(&src).await?;          // ← 못 옮긴 항목이 여기서 소멸한다
```

2026-08-19 에 한 코드베이스에서 같은 형태를 여러 건 만났다 — 폴더 재귀 복사가 항목 오류를 삼켜
**이동이 원본까지 지우던 것**, 청크 업로드가 **자르지 못한 파일을 정상 업로드로 보고**하던 것,
데이터 이전이 **옮기지 못한 파일을 두고 원본 기록을 지우던 것**.

추가로 지킬 것:

- **파괴 단계의 조건을 "성공 응답을 받았다" 가 아니라 "목적지에 전부 있다" 로 바꾼다.** 앞 단계의
  자기 보고가 아니라 **후조건 검증**이 근거가 되어야 한다
- **되돌릴 수 없는 지점을 지난 뒤의 실패**를 특히 조심한다. 쿼터 승인·계정 준비 롤백·인증서 되돌리기처럼
  여기서 오류를 버리면 시스템은 **일관성이 깨진 채로 성공을 보고**한다
- 롤백 자체의 실패도 값이다. "되돌렸음" 을 무조건 기록하면 감사 기록이 거짓이 된다

## 구별할 것

- [[unknown-is-not-absent]]는 **"모름"을 "없음·정상"으로 접는 것** — 조회가 실패했는데 값이 없다고 단정하는 문제다
- 이 노트는 **"일부 실패"를 "전체 성공"으로 접는 것**. 각 단계의 성패는 알고 있는데 그것을 요약하는 과정에서 잃는다

두 결함은 같은 코드베이스에서 나란히 나오지만 고치는 자리가 다르다. 앞은 조회 지점, 뒤는 보고·표현 지점이다.
