# 동기 응답을 작업 접수로 바꿀 때 무너지는 것들

> **TL;DR**: 오래 걸리는 작업을 "끝날 때까지 기다리는 응답" 에서 "접수증을 주고 나중에 알리는 방식" 으로 옮기면, **접수의 원자성**·**재시작으로 끊긴 작업의 정리**·**성공 판정 기준**이 새로 필요해진다. 셋을 안 만들면 응답만 빨라지고 유령 작업이 쌓인다.

## 개요

- **무엇**: 동기 종단점(`DELETE /volumes/1` → 삭제 완료 후 200)을 비동기 작업 접수(`202 Accepted` + `job_id`)로 전환하는 것
- **왜 / 언제**: 작업이 프록시·클라이언트 타임아웃보다 길어질 때. 타임아웃이 나도 **작업은 계속 돌기 때문에**, 호출자가 실패로 읽고 재시도하면 같은 파괴 작업이 두 번 돈다

## 전환하면서 함께 만들어야 하는 것

### 1. 접수의 원자성

접수는 "작업 기록 생성 + 대상 상태를 진행중으로 표시 + 큐 등록" 여러 걸음이다. 중간에 실패하면
**대상은 잠겼는데 아무도 처리하지 않는 상태**가 남는다. 한 트랜잭션으로 묶고, 큐 등록은 커밋 후에 하되
**커밋된 기록을 스캔하는 방식**이면 큐 유실도 견딘다.

### 2. 재시작으로 끊긴 작업의 정리

프로세스가 죽으면 `running` 상태의 기록이 그대로 남는다. **기동 시점에** 그것을 훑어서
`failed`(다시 안 돌 것) 또는 `pending`(재개할 것)으로 정리해야 한다. 이 단계가 없으면 재시작마다
영영 안 끝나는 작업이 늘어난다.

```text
기동 시:
  UPDATE jobs SET status='failed', error='서버 재시작으로 중단됨'
   WHERE status='running' AND worker_id = <이번에 죽었던 인스턴스>;
```

### 3. 성공 판정 기준의 이동

동기일 때는 200 이 곧 완료였다. 이제 202 는 **접수됐다는 뜻뿐**이다.

- 화면은 작업 추적으로 옮기고, **실패 원인 문구가 잘리지 않게** 넉넉히 표시한다
- 기존 시험이 "200 이면 삭제됨" 을 가정하고 있다면 **전부 접수 방식으로 고쳐야 한다**. 안 고치면 시험은
  green 인데 아무것도 검증하지 않는다
- 상한 초과·거부 같은 **접수 자체의 실패**는 여전히 동기 오류로 답한다. 이것을 작업 실패와 섞으면
  클라이언트가 재시도할지 판단할 수 없다

## 주의

> [!WARNING]
> 파괴적 작업일수록 **재시도 안전성(idempotency)** 을 먼저 정해야 한다. 같은 접수가 두 번 들어왔을 때
> 두 번 지울 것인지, 같은 `job_id` 를 돌려줄 것인지. 접수 키를 클라이언트가 정하게 하면 간단해진다.
