# 상호배제는 두 작업이 같은 키를 잠글 때만 성립한다

> **TL;DR**: 두 작업이 각자 락을 걸고 있어도 **잠그는 키가 다르면 서로를 막지 못한다.** 락 코드는 멀쩡해 보이고 시험도 통과하는데, 실제로는 상호배제가 성립하지 않는다. 한 작업이 **두 자리**를 건드린다면 **두 자리를 모두** 잡아야 하고, 여러 자리를 잡을 때는 **잡는 순서를 고정**한다.

---

## 증상

파일을 A → B 로 옮기는 작업과, B 를 지우는 작업이 **동시에 성공했다.**
둘 다 경로 단위 락을 쓰고 있었는데도.

```
이동 작업: A 를 잠금 → A 에서 B 로 복사 시작 …
삭제 작업: B 를 잠금 → 통과(A 락과 겹치지 않음) → B 삭제
이동 작업: 복사 완료 → 기록 남김
⇒ 부분 복사본은 지워졌는데 기록만 남는다
```

## 원인

락의 정확성은 "락을 걸었는가" 가 아니라 **"경합하는 두 경로가 같은 키를 잠그는가"** 로 결정된다.

| 작업 | 잠근 키 | 실제로 건드리는 자리 |
|---|---|---|
| 이동 | 원본 `A` | `A` **와** `B` |
| 삭제 | 대상 `B` | `B` |

이동이 `B` 를 잡지 않았으므로 교집합이 없다. 각자 자기 락은 정상 동작했고, 그래서 **아무도 이상을 눈치채지 못했다.**

## 해결

작업이 건드리는 **모든** 자리를 잡는다.

```rust
/// 상한 + 두 경로 중복 방지. 한 작업이 두 자리를 건드릴 때 쓴다.
/// ⚠️ 잡는 순서를 고정한다(first → second). 이동은 항상 원본 → 목적지.
pub async fn guarded_two_path_op<F, T>(first: &str, second: &str, ...) -> Outcome<T> {
    let Some(g1) = claim_path(first) else { return Outcome::Busy };

    // 같은 경로를 두 번 잡으면 두 번째가 반드시 실패한다 — 자기 자신에게 막히지 않도록 가른다
    let g2 = if first == second {
        None
    } else {
        match claim_path(second) {
            Some(g) => Some(g),
            // 한쪽만 잡은 채로 두지 않는다. g1 은 여기서 drop 되어 풀린다
            None => return Outcome::Busy,
        }
    };
    ...
}
```

세 가지가 함께 필요하다.

1. **자기 충돌 방지** — `first == second` 인 호출부가 있으면 두 번째 획득이 반드시 실패한다
2. **부분 획득 금지** — 두 번째를 못 얻으면 첫 번째도 즉시 놓는다
3. **순서 고정** — 획득이 즉시 실패(non-blocking)라 교착은 구조적으로 없지만, 호출부마다 순서가
   갈리면 **경합에서 어느 쪽이 이기는지가 달라져 재현이 어려워진다**

## 주의

> [!WARNING]
> **락 가드를 호출자 수명에 묶지 마라.** 상한을 넘겨 호출자가 떠나면 점유가 풀리는데 블로킹 작업은
> 계속 돈다 → 같은 자리에 다음 요청이 들어와 또 잠긴다. 가드를 **작업 클로저 안으로** 옮긴다.

> [!WARNING]
> **"두 자리를 잡는 새 헬퍼" 를 만들었으면 기존 한 자리 호출부를 전수로 다시 봐라.** 한 곳만
> 고치면 그 곳과 나머지 사이에 같은 형태의 구멍이 남는다.
