# 보상(Compensation/Saga) 설계 함정 — 프로비저닝 Job에서 실증된 4가지

비동기 다단계 프로비저닝(VM/컨테이너/리소스 생성)에서 실패 시 보상 정리를 설계할 때, "생성 역순으로 지우면 된다"는 직관이 깨지는 지점들. (실기기 리허설 + 적대적 코드리뷰에서 전부 실제 발생)

## 1. 보상 순서는 생성 역순이 아니다 — "자기등록 주체 정지 최우선"

생성된 리소스 안에서 **에이전트가 살아 움직이면**(예: 게스트 안의 데몬이 주기적으로 중앙 DB에 자기등록), DB를 먼저 지워도 몇 초 뒤 되살아난다. 보상 순서는:

```
① 살아있는 주체 정지 (VM destroy / 프로세스 kill)  ← 항상 최우선
② 공유 상태 정리 (DB rows — FK 자식부터)
③ 로컬 산출물 정리 (디스크 파일)
```

②·③은 ①의 성공이 **확인된 경우에만** 진행 — 정지 실패 상태에서 디스크를 지우면 가동 중 리소스의 저장소를 뽑는 셈.

## 2. 조기 실패의 보상은 공유 상태 불가침

이름 중복 검증 같은 **초기 단계에서 실패한 Job의 보상이 이름 기준으로 DB를 지우면**, 동명의 기존 정상 리소스(먼저 성공한 Job의 산출물)를 지운다. 해법: "이 Job이 부작용 단계(에이전트 배포)까지 진행했는가"를 플래그로 기록하고, 그 플래그가 참일 때만 이름 기준 정리를 허용.

## 3. 삭제는 멱등 + 재시도 가능한 순서

삭제 API가 `가상머신 제거 → 디스크 삭제 → DB 삭제` 순서면, DB 단계 실패 시 "리소스는 없는데 레코드는 남은" 상태가 되고 **재시도가 '이미 없음' 에러로 막힌다**. 원칙:

- 제거 계열 명령은 전부 멱등 처리("not found"류를 성공으로)
- 순서는 `주체 제거(멱등) → DB → 디스크` — DB 실패 시 레코드가 남아 재시도 가능, 최악은 고아 디스크 파일(무해, 로그만)

## 4. 외부 자기등록은 FK 그래프째로 흡수

에이전트 자기등록은 부모 행만이 아니라 자식 테이블(인터페이스·라우트 등)까지 만든다. 보상/삭제의 DB 정리는 단독 DELETE가 아니라 **한 트랜잭션의 캐스케이드**(자식 → 부모, 소유권 컬럼은 NULL 해제)여야 FK 위반으로 안 터진다.

## 메타 교훈

- 이런 결함은 **컴파일·단위테스트 전부 통과한 상태**에서 실기기 첫 리허설과 적대적 리뷰("이 코드가 틀렸다고 가정하고 반박하라")에서만 드러났다. 상태기계 + 외부 에이전트 조합은 리허설·적대검증을 기본으로.
