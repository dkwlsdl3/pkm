# 두 서비스가 같은 테이블에 쓰는데 정본이 없으면 유령 행이 생긴다

> **TL;DR**: 서로 다른 두 서비스가 같은 테이블에 upsert하고 **등록 키를 각자 계산**하면, 계산 결과가 갈리는 순간 같은 대상이 두 행이 된다. 지금 안 터진다면 그건 설계가 아니라 **키가 우연히 일치하고 있는 것**이다.

## 증상

- 관리 화면에 같은 대상이 **두 행**으로 보인다. 한쪽은 정보가 일부만 채워져 있다.
- 한 환경에서만 재현되고 다른 환경에서는 멀쩡하다.
- 어느 쪽이 "진짜"인지 코드를 봐도 안 나온다 — **양쪽 다 자기가 맞다고 쓰고 있다.**
- 지운 대상의 행이 영원히 남는다. **어느 서비스도 남의 행을 지우지 않기 때문이다.**

## 원인

같은 테이블에 두 writer가 있고, 셋 중 하나 이상이 정의돼 있지 않다.

| 정의돼야 하는 것 | 정의 안 되면 |
|---|---|
| **등록 키를 누가 정하는가** | 계산식이 갈리면 같은 대상이 두 행 |
| **어느 컬럼을 누가 소유하는가** | 겹치는 컬럼을 서로 덮어쓴다 |
| **행을 누가 지우는가** | 아무도 안 지워 고아 행이 영구 누적 |

전형적인 형태는 이렇다.

```text
서비스 A (먼저 있었음)   →  이름·표시명·시간대만 씀,  이름 = hostname
서비스 B (나중에 붙음)   →  위 3개 + 역할·주소·상태, 이름 = 환경변수 우선, 없으면 hostname
                             ↑ 같은 테이블에 upsert, 키는 '이름'
```

두 서비스는 대개 **시기가 달라서** 이렇게 된다. A가 먼저 있었고 나중에 B가 같은 테이블을 재사용하면서, 각자 아는 정보만 쓰다 보니 지금 모양이 된다. 컬럼이 안 겹치는 것은 **설계가 아니라 우연**이다.

⚠️ **"실환경에서는 문제가 없다"가 안전의 근거가 되지 못한다.** 위 예에서 실환경에는 그 환경변수가 아무 데도 설정돼 있지 않아 양쪽이 같은 값을 냈다. **한쪽에만 그 값을 주는 순간 어느 환경에서든 갈라진다.** 설정 하나가 데이터 정합을 지탱하는 상태다.

⚠️ 서비스 B가 **API 서버를 거치지 않고 DB에 직접 쓰는** 구조라면 증상 추적이 더 어렵다. 애플리케이션 로그에 흔적이 남지 않아, 출처 불명의 행이 "원인 미상"으로 남는다.

## 해결

세 방향이 있고, 비용과 근본성이 다르다.

**① 한쪽을 정본으로 지정** — 대상에 대해 가장 많이 아는 쪽(위 예에서는 B)이 등록·삭제를 전담하고, 다른 쪽은 자기 도메인 데이터만 쓴다. 정본이 없는 대상은 누가 등록하느냐가 남는다.

**② 쓰기 창구를 하나로** — 둘 다 API 서버에 보고하고 API 서버만 DB에 쓴다. 가장 깨끗하고 가장 크다. 직접 DB 접속을 없애면 접속 정보 배포 문제도 같이 없어진다. 대신 통신 경로가 필요하다.

**③ 소유 컬럼을 명시** — 지금 구조를 두고 "누가 어느 컬럼을 쓰는지" 못 박아 남의 컬럼을 안 건드리게 한다. 가장 싸지만 **키 분기 문제는 그대로 남는다.**

어느 쪽이든 **먼저 해야 할 것은 키 계산을 한 곳으로 모으는 것이다.** 키를 각자 계산하는 한 나머지 정리는 증상 완화에 그친다.

**즉시 할 수 있는 방어**
- 등록 키 계산 로직을 공유 모듈로 빼고, 환경변수 같은 우회 입력을 **양쪽에서 동일하게** 취급한다
- 고아 행 탐지 쿼리를 만들어 주기적으로 확인한다 — 지금 몇 개 있는지 모르는 상태가 제일 나쁘다
- 삭제 연쇄(`ON DELETE CASCADE`)를 정의한다. 안 걸려 있으면 고아 행 하나 지우는 데 관련 테이블을 손으로 다 훑어야 한다
