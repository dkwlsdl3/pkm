# 외부 명령 Hang 격벽 (Timeout Bulkhead)

> **TL;DR**: 외부 CLI/원격 호출은 언젠가 **무기한 hang**한다. hang 자체보다 무서운 건 전이다 — DB 트랜잭션/락을 쥔 채 기다리면 커넥션 풀이 말라 **무관한 요청까지 전면 마비**된다. ①모든 외부 명령을 타임드 래퍼(timeout+강제 kill)로 감싸고 ②락/트랜잭션 보유 구간 밖에서 실행하며 ③"명령 성공"이 아니라 "원하는 최종 상태"를 검증한다.

---

## 문제: 단일 hang의 전면 장애 전이

```
요청 → tx 시작(커넥션 점유) → 외부 CLI 실행 … hang
요청 → tx 시작(커넥션 점유) → 외부 CLI 실행 … hang
…(반복)… → 커넥션 풀 고갈 → 외부 명령과 무관한 모든 API까지 죽음
```

스토리지·클러스터 관리 도구처럼 커널/네트워크에 닿는 CLI(파일시스템 질의, 디바이스 조작)는 대상 장애 시 **에러가 아니라 무응답**으로 실패하는 경우가 많다. D-state 프로세스는 SIGTERM도 안 먹는다.

## 패턴

1. **타임드 래퍼 단일화**: 외부 명령 실행 헬퍼를 하나로 모으고(timeout, 만료 시 SIGKILL, stderr 수집), 무방비 직접 호출을 lint/리뷰로 금지한다. timeout 값은 명령 종류별로 명시.
2. **락·트랜잭션 밖 실행**: DB 트랜잭션이나 전역 락 보유 구간에서 외부 명령을 기다리지 않는다. 필요하면 "예약 행 기록(tx 짧게) → 락 해제 → 외부 명령 → 결과 반영(tx 짧게)" 3단계로 쪼갠다. 실패 시 예약 행 회수(고스트 정리)까지 설계에 포함.
3. **후조건 검증**: 명령 exit 0/성공 응답이 아니라 **최종 상태**(마운트 목록, 디바이스 목록, 설정 파일)를 다시 조회해 판정한다. "A or B 성공" 같은 OR 판정은 부분 성공 상태를 성공으로 오인하기 쉽다 — 후조건은 AND로.
4. **fail-closed 전파**: 격벽에 걸려 실패한 작업은 삼키지 말고 호출자에 실패로 전파해, 후속 파괴 단계가 진행되지 않게 한다.

## 판정 기준

- 이 외부 명령이 10분 hang하면 시스템의 어디까지 죽는가? — "그 요청 하나"가 답이 아니면 격벽이 없는 것.
- blkid, statfs류 "가벼운 조회"도 대상 디바이스가 불량이면 D-state로 멈춘다 — 조회라고 예외 아님.
