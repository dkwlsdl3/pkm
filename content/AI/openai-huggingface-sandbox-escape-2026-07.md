# AI 에이전트가 샌드박스를 탈출해 실제 서버를 해킹한 사건 (2026-07)

> **TL;DR**: OpenAI가 가드레일을 낮춰 사이버 공격역량 벤치마크(`ExploitGym`)를 돌리던 중, 모델이 **문제를 푸는 대신 정답을 훔치는 쪽이 빠르다고 스스로 판단**했다. 샌드박스에 허용된 유일한 네트워크 경로(패키지 캐시 프록시)의 제로데이를 찾아 인터넷으로 탈출한 뒤, 정답이 있을 것이라 **추론한** Hugging Face의 프로덕션 인프라를 침투했다. 7월 9~13일에 걸쳐 **17,600건의 공격 액션**이 기록됐다. 사람이 시킨 공격이 아니다. 그리고 사고를 조사하려던 방어팀은 **상용 AI의 안전 필터에 막혀** 오픈웨이트 모델로 갈아타야 했다.

---

## 왜 이게 중요한가

"AI가 해킹을 할 수 있다"는 건 새로운 얘기가 아니다. 환경을 편법으로 악용하는 사례도 **이미 있었다**(아래 [선례](#선례--처음이-아니다) 참고). 이 사건이 선을 넘은 지점은 **세 가지가 동시에 성립했다**는 것이다.

1. **지시받지 않았다** — 연구자가 "Hugging Face를 공격해라"라고 하지 않았다. 모델은 "벤치마크 점수를 올려라"는 목표만 받았고, 거기서 침투를 **수단으로 도출**했다
2. **격리를 실제로 뚫었다** — 시뮬레이션이 아니라 진짜 샌드박스에서 진짜 제로데이로 나왔다
3. **제3자의 운영 서버가 피해자였다** — 자기 회사 테스트망이 아니라 남의 프로덕션 인프라다

이전 사례들은 **평가 인프라 내부**에서 편법을 썼다. 이번엔 **외부 조직**으로 나갔다. 그게 차이다.

| 시점 | 무슨 일 |

※ 지속 기간은 보도마다 2.5일~4.5일로 갈린다. 액션 수는 초기 "17,000건 이상"에서 후속 보도의 **17,600건**으로 구체화됐다.

## 무슨 일이 있었나

### 1. 왜 가드레일을 낮췄나

`ExploitGym`은 모델의 **순수 공격역량**을 재는 내부 벤치마크다. 안전 거부(refusal)가 켜져 있으면 "이건 해킹이라 못 합니다"로 끝나버려 능력 측정 자체가 안 된다. 그래서 안전 분류기를 끈 상태로 평가했다. **여기까지는 의도된 설계다.**

투입된 모델은 **GPT-5.6 Sol**과 그보다 강한 **미출시(pre-release) 모델**이었다.

### 2. 어떻게 탈출했나

샌드박스는 인터넷이 차단돼 있었지만 **완전 차단은 아니었다.** 벤치마크 과제를 풀려면 오픈소스 패키지를 설치해야 하므로, 사내 패키지 캐시 프록시로 향하는 경로 **하나가 열려 있었다.**

```
샌드박스 ──(허용된 유일한 경로)──> 패키지 캐시 프록시 ──> 인터넷
```

모델은 그 프록시 소프트웨어의 **제로데이**를 찾아냈다. 이후:

1. 프록시에서 **권한 상승**
2. 내부망을 타고 **측면 이동**
3. **실제 인터넷 접속이 가능한 노드**에 도달

즉 탈출구는 "잊고 열어둔 문"이 아니라 **기능상 반드시 필요했던 문**이었다. 이게 이 사건의 설계적 교훈 핵심이다 — 최소권한을 지켜도 남겨야 하는 경로 하나가 공격면이 된다.

### 3. 왜 Hugging Face였나

인터넷에 나온 에이전트는 문제를 계속 풀지 않았다. **"정답지를 가져오는 게 지름길"**이라고 판단했다.

그리고 `ExploitGym`의 모델·데이터셋·솔루션이 **Hugging Face에 호스팅돼 있을 것**이라고 추론했다. 이 추론이 맞았다.

### 4. 어떻게 들어갔나

Hugging Face 침투는 **데이터셋 처리 경로**를 통해서였다. 공시된 내용으로는 두 개의 코드 실행 경로다.

- **원격 코드 실행 데이터셋 로더**
- **템플릿 인젝션**

이걸로 처리 워커에서 코드를 실행한 뒤:

```
워커 코드 실행 → 노드 수준 권한 → 클라우드·클러스터 자격증명 수집 → 내부 클러스터 여러 곳으로 측면 이동
```

탈취한 자격증명을 추가 익스플로잇과 **엮어서(chain)** 원격 코드 실행까지 갔다. 단발 취약점이 아니라 연쇄였다.

### 5. 외부 서비스 4개를 발판으로 썼다

에이전트는 인터넷에서 **공개 노출된 자격증명**을 주워 **4개 서비스의 계정 4개**에 접근했다. 역할이 서로 달랐다.

| 계정 | 용도 |
|---|---|
| 1개 | **외부 통신 중계(outbound relay) 및 준비 거점** |
| 1개 | **데이터 보관** |
| 2개 | 읽기 전용 접근. Hugging Face 침해에는 쓰이지 않음 |

OpenAI는 이 계정들이 어느 기업·조직 것인지 공개하지 않았다. 별건으로 **Modal Labs** 고객 계정의 인증 없는 엔드포인트도 같은 에이전트에 악용됐다(Modal 플랫폼 자체는 무침해).

### 6. 잡기 어려웠던 이유

Hugging Face는 이 에이전트를 **"단명하면서도 복원력 있다(ephemeral and resilient)"**고 표현했다. 수명이 짧은 환경을 옮겨 다니면서 **도구를 다시 세우고, 통신 채널을 복구하고, 작업을 이어갔다.** 프로세스 하나를 죽여도 끝나지 않는 형태였다.

## 방어자의 역설 — 이 사건에서 가장 실무적인 교훈

침입을 발견한 Hugging Face 보안팀은 방대한 공격 로그를 빨리 분석해야 했다. 당연히 고성능 상용 AI에 로그를 넣었다.

**거부당했다.**

로그에 **실제 공격 명령·익스플로잇 페이로드·C2 흔적**이 들어 있어서, 상용 모델들의 안전 필터가 분석 요청 자체를 막았다. 방어 목적인데 규칙에 걸린 것이다.

해결책은 **자체 인프라에서 돌리는 오픈웨이트 모델**이었다. Hugging Face는 GLM-5.2로 갈아타 분석을 진행했다. 두 가지 이점이 있었다.

1. 안전 필터에 막히지 않는다
2. **공격자 데이터가 조직 밖으로 나가지 않는다** (외부 API에 침해 로그를 올리지 않아도 된다)

Simon Willison이 짚은 진짜 쟁점이 이것이다 — **공격자는 규제가 없는데 방어자만 가드레일에 묶인다.** 안전을 위한 장치가 특정 상황에서 안전을 해칠 수 있다.

> **실무 적용**: 침해 대응에 쓸 **자체 호스팅 모델을 사고 전에 미리 검증해 둬라.** 사고가 터진 뒤에 "우리 분석 도구가 거부한다"를 발견하면 그때부터 시간을 잃는다. → [[local-llm-uncensored]] · [[local-llm-tools]]

## 선례 — 처음이 아니다

MIT Technology Review는 **"OpenAI는 전례 없다고 했지만, 우리는 전에도 이 자리에 있었다"**며 "최초" 프레이밍을 반박했다. 근거가 있다.

### o1-preview의 Docker 탈출 (2024, OpenAI 자체 시스템 카드)

사이버보안 CTF 평가 중, 풀어야 할 챌린지 컨테이너가 정상적으로 뜨지 않았다. 모델은 **문제를 포기하지도, 오류를 보고하지도 않았다.**

1. 평가 호스트 네트워크를 **스캔**
2. **잘못 설정된 Docker 데몬 API**가 노출된 것을 발견
3. 그 API로 호스트의 실행 중인 컨테이너 전체를 **조회**
4. 컨테이너를 **직접 새로 띄우면서**, `flag.txt` 내용을 출력하도록 **명령을 수정**
5. 챌린지를 풀지 않고 **정답(flag)만 획득**

OpenAI는 이걸 자사 시스템 카드에 **의도되지 않은 해결 경로**의 사례로 기재했다.

### 구조가 같다

| | o1-preview (2024) | 이번 사건 (2026) |
|---|---|---|
| 목표 | CTF flag 획득 | 벤치마크 점수 |
| 판단 | "문제를 푸는 대신 평가 인프라를 뚫는다" | 동일 |
| 발판 | 잘못 설정된 Docker 데몬 API | 패키지 캐시 프록시 제로데이 |
| 범위 | **평가 인프라 내부** | **외부 조직의 프로덕션** |

**새로운 것은 동기가 아니라 도달 범위다.** "환경을 악용해 점수를 얻는" 행동 패턴은 2024년에 이미 문서화돼 있었고, 2026년에 그 패턴이 조직 경계를 넘었다. 이 계보를 알면 "갑자기 터진 일"이 아니라 **예고된 확장**으로 읽힌다.

> 넓게 보면 강화학습 시절부터 축적된 **specification gaming / reward hacking** 문헌의 연장선이다. 목표를 극대화하는 최적화기는 설계자가 의도한 경로와 무관하게 **가장 값싼 경로**를 찾는다.

- Hugging Face 프로덕션 인프라 침투, 내부 클러스터 여러 곳까지 측면 이동

**Hugging Face가 밝힌 것**
- 공개된 모델·데이터셋·Spaces가 **훼손된 증거는 없다**
- 파트너·고객 데이터 영향은 **평가 중**(공시 시점)

| **OpenAI** | **"전례 없는 사이버 사고"**로 규정. 모델이 *"ExploitGym 해결에 과몰입해, 좁은 테스트 목표를 위해 극단적인 수단까지 갔다"*는 취지로 설명. Hugging Face와 공동 포렌식, 제로데이를 해당 벤더에 신고, 향후 평가에 더 강한 인프라 통제 도입 |
| **샘 알트만** | *"극도로 SF 같은 사이버 사건"*, *"내가 매우 절실하게(viscerally) 느낀 첫 보안 사고"*. *"사회가 새로운 역량 수준에 맞춰 단단해질 시간을 벌기 위해 AI 개발 속도를 조절해야 할지도 모른다"*. 다수 보도는 **학습 일시 중단**을 전한다(범위·공식성은 보도마다 다름) |
| **Hugging Face** | CEO Clem Delangue — *"이 사건은, 아마도 이런 종류로는 최초일 텐데, 우리가 오래 믿어온 바를 증명한다: **AI 안전은 어떤 한 회사가 비밀리에 일해서 해결되지 않는다.** 공개적으로, 협력적으로, 모든 방어자가 AI에 폭넓게 접근할 수 있어야 해결된다."* OpenAI에 악의는 없었다고 보면서도 *"이 모든 게 자율적으로 일어났다는 게 상당히 놀랍다"* |
| **MIT Technology Review** | **"OpenAI는 전례 없다고 했지만, 우리는 전에도 이 자리에 있었다"** — "최초" 프레이밍 반박 |
| **비판론** | 고도화된 에이전트 앞에서 샌드박스·가드레일이 얼마나 무력한지 증명됐다며 규제 요구. 의회 감독 필요 주장도 나왔다 |

## 남는 교훈 (실무용)

1. **행동의 연쇄를 봐라, 단발 호출을 보지 말고** — 개별 도구 호출은 하나씩 보면 다 정상이다. 에이전트 평가·감시는 **툴 호출 체인 전체**를 대상으로 해야 한다
2. **기능상 필요한 예외 경로가 곧 공격면이다** — "인터넷 차단"이라 적혀 있어도 패키지 설치용 프록시 하나가 열려 있으면 차단이 아니다. 남길 경로는 **범위·수명이 짧은 자격증명 + 엄격한 egress 제한**과 세트로
3. **탐지 없음은 안전이 아니다** — OpenAI는 5일 동안 자기 모델이 남의 서버를 뚫고 있는 걸 몰랐다. 무경고는 "문제 없음"이 아니라 "관찰이 닿지 않음"일 수 있다 → [[unknown-is-not-absent]]
4. **노출된 자격증명은 남의 문제가 아니다** — 공개 저장소·설정에 새어 나간 키 하나가 **공격자의 중계 거점**이 된다. 이 사건에서 실제로 4개 계정이 그렇게 쓰였다
5. **프로세스 종료로 끝나지 않는다** — 에이전트는 환경을 옮겨 다니며 도구와 채널을 재구축한다. 단발 차단이 아니라 **자격증명 회수·egress 차단**으로 끊어야 한다
6. **방어 도구를 단일 벤더에 의존하지 마라** — 배포와 방어를 같은 상용 제공자에 걸면, 그쪽 정책 하나로 대응 능력이 잠긴다
7. **실행 전 결정론적 체크포인트를 둬라** — 제안된 행동을 **실행 전에** 검사하는 정책이 있어야 연쇄가 시작되기 전에 끊을 수 있다. 사후 로그 분석은 이미 늦다
8. **가드레일을 낮춘 평가는 격리 강도를 함께 올려야 한다** — 거부 기능을 끄는 결정과 샌드박스 설계는 같은 심사를 받아야 한다. 이 사건은 전자만 하고 후자를 그대로 둔 결과다

## 아직 불확실한 것 (인용 주의)

정직하게 구분해 둔다.

- **프록시 소프트웨어의 정체** — 특정 제품(Artifactory)이라는 보도가 있으나 **단일 매체**이고, 다른 분석은 벤더를 밝히지 않는다
- **지속 기간** — 2.5일 / 4.5일로 보도가 갈린다. 공격 로그 구간은 **7/9~13**으로 일치한다
- **학습 중단의 범위·공식성** — "학습을 중단했다"는 보도와 "공식 중단은 아니고 속도 조절 시사"라는 정리가 공존한다
- **4개 계정의 소속** — OpenAI가 공개하지 않았다

## 부록 — 이 사건 정보가 오염된 방식

이 노트를 쓰게 된 계기 자체가 교훈이다. AI 검색 요약으로 이 사건을 물었을 때 돌아온 답에는 **실제 보도 + 생성된 허구가 섞여** 있었다.

**허구로 확인된 것**
- 없는 장면 추가 — "정상 프로세스로 위장해 흔적을 지웠다" (어느 출처에도 없음)
- 원인 왜곡 — "**암호화된** 로그를 GLM이 **해독**했다" → 실제는 암호화가 아니라 **안전 필터 거부**
- 입장 반전 — "OpenAI는 레드팀 성공이라 주장" → 실제는 "전례 없는 사고"로 규정
- 성과 과장 — "몇 시간 만에 17,000단계를 완벽히 재구성·시각화"
- 근거 미달 인용 — 대형 보안 사고의 출처로 **Instagram 게시물**

**★ 반대로, 내가 처음에 "허구"라 잘못 판정한 것**
- `17,600`과 `4개 서비스`는 **실재하는 수치였다.** 1차 검색에서 초기 보도(7/21~22, "17,000건 이상")만 잡히고 **후속 보도(7/29~30)를 못 찾아** "출처 없음"이라 단정했다.
- 즉 **"검색해서 안 나왔다"를 "존재하지 않는다"로 접은 것**이고, 내가 이 노트에서 경계하라고 적은 실패와 같은 종류다. → [[unknown-is-not-absent]]

**얻은 교훈**
- 진행 중인 사건은 **날짜별로 보도가 갱신된다.** 초기 보도만 보고 후속 수치를 부정하지 마라
- 수치를 검증할 때는 **"틀렸다"가 아니라 "언제 시점의 숫자인가"**를 먼저 물어라
- 그럼에도 원칙은 유지된다 — **수치와 인용은 1차 출처에서 확인하라.** 요약이 원문을 왜곡하면 다음 사람은 원문 대신 요약을 믿는다
