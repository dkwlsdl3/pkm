# 이종 모델 교차 워크플로 (Claude ↔ Codex)

> **TL;DR**: 설계·구현·검증을 서로 다른 모델에 나눠 맡기면 같은 모델을 반복 호출할 때보다 결과가 낫다. 같은 모델은 같은 맹점을 공유하기 때문이다.

---

## 개요

- **무엇**: Claude Code와 Codex를 역할 분담해 한 작업을 통과시키는 방식
- **왜 / 언제**: 혼자 설계하고 혼자 검증하면 자기 전제를 다시 밟는다. 판단 근거가 약하거나 되돌리기 비싼 변경일 때 다른 모델을 검증자로 세운다.

## 두 가지 패턴

**A. 설계(Claude) → 구현(Codex) → 검증(Claude)**

설계 의도를 아는 쪽이 결과를 받아 보므로 "명세와 다르게 구현된 부분"이 잘 잡힌다. 구현 분량이 크고 명세가 이미 확정된 작업에 맞다.

**B. 설계 + 구현(Claude) → 적대적 검증(Codex)**

맥락이 이미 한쪽 컨텍스트에 있을 때 위임 비용(재전달·손실)을 치르지 않는다. 검증만 다른 모델에 넘긴다. 대신 검증자는 코드와 명세만 보고 판단하므로, 무엇을 검증할지 축을 지정해줘야 노이즈가 줄어든다.

두 경우 모두 검증은 read-only로 지시하고, 반박 유도형으로 프롬프트한다 → [[subagent-adversarial-crosscheck]]

## 왜 같은 모델보다 나은가

동일 모델의 서브에이전트는 컨텍스트만 다르고 판단 편향은 같다. 잘못된 전제를 통과시키는 지점도 대체로 겹친다. 다른 모델은 틀리는 지점이 달라서, 한쪽이 놓친 것을 다른 쪽이 잡을 확률이 올라간다.

관측된 것은 "결과가 더 좋았다"는 수준의 경험적 판단이고, 측정된 수치는 아니다.

## 스킬로 고정해 둔 호출

Claude에서 Codex를 호출하는 쪽으로 스킬을 만들어 두었다. 역방향은 Codex 쪽 `claude-review`.

| 스킬 | 용도 |
|---|---|
| `delegate` | 정밀 프롬프트를 작성해 구현을 Codex에 위임 |
| `review` | Claude의 결론을 Codex가 적대적으로 반박 |
| `consensus` | 양쪽 의견을 주고받아 합의안 도출 |
| `debate` | 일부러 대립 관점을 세워 맹점 노출 |

## 한쪽을 못 쓸 때의 대체

한쪽 도구의 사용량 한도가 소진되면 이종 검증이 불가능해진다. 이때는 같은 모델 서브에이전트를 적대적 검증자로 세워 진행한다. 형태는 유지되지만 편향이 공유되므로 검증 강도는 떨어진다 — 통과했다는 사실에 이종 검증만큼 무게를 두지 않는다.

## 주의

> [!WARNING]
> 검증자를 세운다고 검증이 되는 것은 아니다. 확신이 없으면 "refuted=true 기본"처럼 통과 기준을 올려 지시해야 한다. 근거 없는 동의도 동의로 보이기 때문이다.
