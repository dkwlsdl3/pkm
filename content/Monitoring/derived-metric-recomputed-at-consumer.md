# 소비 측이 파생값을 다시 계산하면 생산 측 정의 수정이 그 자리에서 되돌아간다

> **TL;DR**: 화면이 `여유 = 전체 − 사용` 처럼 **API 가 이미 준 값을 다시 만들면**, 수집기의 정의를 바로잡는 순간 그 화면만 옛 정의로 남는다. 소비 측은 준 값을 그대로 쓰고, **없으면 재구성하지 말고 "데이터 없음"으로 그린다.**

## 증상

- 백엔드 수집기 정의를 고쳐 API 응답은 맞는데 **특정 화면 하나만** 옛 값을 보여준다
- 세 값(전체·사용·여유) 중 둘만 맞고 나머지 하나가 나머지 둘의 뺄셈으로 나온다
- API 응답에 필드가 없을 때 화면이 0 이나 100% 같은 **그럴듯한 거짓값**을 그린다

## 원인

파생값을 만드는 자리가 **둘**이기 때문이다. 생산 측(수집기·API)과 소비 측(화면·집계기)이
같은 관계식을 각자 들고 있으면, 그 관계식이 **더 이상 성립하지 않게 되는 변경**에서 갈라진다.

실측 사례: 디스크 사용량 정의를 `df` 와 맞추자 **`사용 + 여유 < 전체`** 가 정상이 됐다([[statvfs-used-vs-df-reserved-blocks]]).
그런데 대시보드가 여유를 `전체 − 사용` 으로 재구성하고 있어서, 사용량을 바로잡는 순간
**그 자리에는 쓸 수 없는 예약분까지 여유로 표시**됐다. 고치기 전보다 나빠진 것이다.

여기서 위험한 것은 관계식이 **평소에는 맞는다**는 점이다. 그래서 코드 리뷰에서 눈에 안 띄고,
정의가 바뀌는 딱 그 순간에만 틀린다.

## 해결

- **API 가 준 값을 그대로 쓴다.** 소비 측에 관계식을 복제하지 않는다.
- 값이 **없으면 만들지 않는다.** 재구성 대신 "데이터 없음"으로 그린다 — 없는 것을 계산해 채우면 그 화면은 이후 영영 검증되지 않는다.
- 정의를 바꿀 때는 **그 값을 읽는 쪽을 먼저 찾는다.** 생산 측 커밋과 소비 측 커밋이 갈리면 그 사이 배포에서 화면이 틀린다.
- 어쩔 수 없이 파생을 소비 측에서 해야 하면, **관계식이 성립한다는 사실 자체를 시험으로 고정**한다(`사용 + 여유 == 전체` 를 단언하는 시험이 있었다면 이 변경에서 실패해 소비 측을 같이 보게 된다).
