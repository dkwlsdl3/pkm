# 기동 직후 수집 전 상태를 장애로 신고한다

> **TL;DR**: 감시 프로세스가 올라온 직후에는 아직 아무것도 수집하지 않았다. 이때 판정 함수가 **비어 있는 상태를 "정상이 아님"으로 읽으면** 첫 라운드에서 대량의 거짓 경보가 나간다. 재시작·배포 때마다 반복되므로 사람이 경보를 무시하게 된다. **미수집은 정상도 장애도 아닌 제3의 상태**로 두어야 한다.

## 용어

| 표기 | 원어 | 뜻 |
|---|---|---|
| 콜드 스타트 | cold start | 프로세스가 막 시작해 캐시·이력이 비어 있는 구간 |
| 판정 함수 | — | 수집값을 받아 정상/경고/장애를 내는 함수 |
| 경보 피로 | alert fatigue | 거짓 경보가 반복돼 사람이 경보 전체를 무시하게 되는 상태 |

## 증상

- 감시 데몬을 재시작할 때마다 경보가 한 번씩 몰려 나간다. 몇 초 뒤 자동으로 해제된다.
- 배포 직후 "전체 장애"처럼 보이는 알림이 오지만 실제로는 아무 문제가 없다.
- 이 패턴이 반복되면서 팀이 **기동 직후 경보는 무시한다**는 암묵 규칙이 생긴다 — 진짜 장애도 같이 묻힌다.

## 원인

판정이 `Option`/빈 맵/0 을 **값으로** 받아들이기 때문이다.

```text
// 위험한 형태
let health = latest_status.unwrap_or(Status::Unhealthy);   // 미수집 → 장애
let used = metrics.get("used").copied().unwrap_or(0);      // 미수집 → 0

// 기본값이 "안전한 쪽"처럼 보여서 이렇게 쓰게 된다.
// 그러나 미수집을 장애로 접으면 거짓 경보, 정상으로 접으면 진짜 장애를 놓친다.
// 어느 쪽으로 접어도 틀린다 — 접지 말아야 한다.
```

같은 형태가 **수집 실패 회차**에서도 나온다. 한 라운드의 수집이 실패했는데 직전 값과 섞어 쓰면, 상태와 속성이 **서로 다른 시점**을 가리키게 된다.

## 해결

```text
1) 상태를 셋으로 나눈다 — 정상 / 장애 / 미수집(unknown)
   판정 함수의 반환 타입에 미수집을 넣고, 기본값으로 접는 코드를 지운다

2) 경보 규칙에서 미수집을 따로 다룬다
   - 기동 후 첫 N 라운드: 경보하지 않는다
   - 그 뒤로도 계속 미수집: "수집이 안 된다"는 별도 경보 (장애 경보와 문구가 다르다)

3) 한 회차의 값은 한 시점에서만 만든다
   수집 실패 시 직전 값으로 부분 보충하지 않는다. 회차 전체를 미수집으로 둔다
```

> [!WARNING]
> **"모른다"를 장애로 접든 정상으로 접든 둘 다 틀린다.** 접는 방향을 고르는 문제가 아니라, 접지 않고 전달하는 문제다 → [[unknown-is-not-absent]] · [[timeout-is-unknown-not-failure]]

> [!WARNING]
> 첫 라운드 억제(suppression)를 넣을 때 **억제 구간이 끝난 뒤에도 미수집이면 반드시 알려야 한다.** 억제만 넣고 후속 경보를 안 만들면 이번에는 수집 중단이 영영 안 보인다.
