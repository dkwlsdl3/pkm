# WebSocket 재연결 예산은 "안정적으로 유지됐다"로 리셋한다

> **TL;DR**: 재연결 시도 예산을 `onopen`에서 즉시 리셋하면, **붙자마자 끊는 서버(flapping)에 영원히 재연결한다** — 상한이 사실상 "연속 handshake 실패"만 센다. 리셋 조건을 "붙어서 `stableAfter`(예: 5초)만큼 유지됐다"로 바꾼다. 그리고 `CONNECTING`에 머무는 소켓은 close·error가 오지 않아 재연결 체인이 **영구 정지**하므로 `connectTimeout`으로 강제 종료해 평소 close 경로로 흘려보낸다.

---

## 결함 ① 무한 재연결 (flapping)

```js
// 안티패턴
ws.onopen = () => { attempts = 0; ... }   // 붙는 즉시 예산 리셋
```

서버가 연결을 받아주고 곧바로 끊는 상태에서는 **매 회차 시도 상한이 되살아난다.** 지수 백오프도 리셋되므로 기본 간격(예: 3초)으로 **영원히** 두드린다. 백엔드가 고장 났을 때 정확히 이 상태가 된다.

```js
// 수정: 안정화된 뒤에만 성공으로 센다
ws.onopen = () => {
  stableTimer = setTimeout(() => { attempts = 0 }, stableAfter)  // 기본 5000ms
}
```

안정화 전에 끊긴 연결은 성공으로 세지 않으므로 지연이 계속 늘어나 상한에서 멈춘다. 정상 연결(오래 유지)의 리셋 동작은 그대로다.

## 결함 ② 연결 영구 정지 (CONNECTING)

`CONNECTING` 상태에 머무르는 소켓에는 **close도 error도 오지 않는다.** 재연결은 보통 `onclose`에 걸려 있으므로 체인이 아예 돌지 않고 화면이 조용히 멈춘다.

```js
// 수정: 연결 제한시간을 두고 강제로 닫아 평소 경로로 보낸다
connectTimer = setTimeout(() => {
  if (ws && ws.readyState === WebSocket.CONNECTING) ws.close()  // → onclose → 백오프 재연결
}, connectTimeout)   // 기본 10000ms
```

열린 뒤에는 이 타이머가 소켓을 닫지 않도록 해제한다. 소켓 수명에 딸린 타이머는 close·교체·명시적 해제 때 **함께 정리**한다(`clearSocketTimers`). 세대가 엇갈려 남은 타이머는 identity 가드가 no-op으로 흡수한다(콜백이 자기 소켓만 만진다).

## 결함 ③ `disconnect()`가 환경에 따라 갈린다

명시적 해제의 콜백 동작이 **테스트와 실브라우저에서 반대로** 나온다.

- 브라우저는 close 이벤트를 **task로 큐잉**한다(WHATWG WebSockets)
- 테스트 mock은 close를 **동기로** 부르는 경우가 많다

```js
// 순서에 따라 결과가 갈린다
ws.close(); ws = null;   // 브라우저: 나중에 온 close가 identity 가드에 걸려 onClose 미호출
                         // 동기 mock: 즉시 close → onClose 호출 (폴링 재개!)
```

→ **참조를 먼저 끊고 닫아** "명시적 해제는 항상 콜백 없이 조용히 끝난다"로 의미를 고정한다. 상태 전이는 `disconnect`가 직접 책임진다.

```js
const sock = ws; ws = null; sock.close();
```

## 중복 제거 시 함께 확인할 것

여러 소비자가 재연결 로직을 **복사해** 갖고 있으면, 한쪽의 결함 수정이 복사본에 반영되지 않는다(실제로 4건이 한쪽에만 반영됐다). 저수준 프리미티브로 추출할 때:

- core는 프레임워크 컴포저블을 **직접 부르지 않는다**(URL 생성은 콜백으로) — 모듈 스코프 싱글턴에서도 쓸 수 있어야 한다
- **오류 경계를 좁히지 마라**: URL 생성 호출이 `try` 밖으로 나가면 주소 생성 실패가 '생성 실패'로 처리되지 않고, 수동 연결에서는 예외가 호출자까지 튀고 자동 재연결 타이머에서는 체인이 조용히 끊긴다
- 수동 재연결 전용 소켓(터미널 등)은 **중복 제거 대상이 아니다** — 백오프 로직이 없고 고유 요구(arraybuffer·종료코드 분기)가 있다
- 죽은 코드를 확인하라: "재연결을 막으려 시도횟수를 최대로 올린 직후 같은 함수에서 0으로 되돌리는"(close는 그 뒤 비동기 도착) 형태는 **"해제했는데 다시 붙는"** 잠재 결함이다

## 테스트 주의

- **개수만 세는 테스트는 무의미하다** — "10회 이하"는 예산이 매 회차 리셋되는 구현도 통과한다(각 구간이 10회 이하이므로). **지연 경계를 직접 재라**(예: 1,999ms vs 1ms)
- **기본값 전용 테스트를 따로 둔다** — 실제 소비자는 옵션을 넘기지 않고 기본값에 의존하므로, 기본값을 0으로 꺼도 아무도 못 잡는다
- 늦게 도착하는 close는 **비동기 close mock**으로 실제 순서를 재현한다(중복 close에 의존하는 테스트는 실제 이벤트 순서를 증명하지 않는다)
- 라이브 확인: 프레임 수신 + 연결 배지 + 콘솔 에러 0 + **화면 이동 시 소켓이 닫히는지**(언마운트 해제 경로)
