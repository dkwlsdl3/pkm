# "자동화 불가" 는 케이스 유형 이름이 아니라 조작 내용으로 판정한다

> **TL;DR**: 시나리오 표의 **유형 열**(중단·이탈 / 동시성 / 순서 이상)을 보고 "브라우저 자동화로는 못 한다"고 판정하면 대량 오분류가 난다. 실측: 불가 판정 **2783 → 1058 → 최종 243**. 유형 이름이 아니라 **각 행이 실제로 시키는 조작**을 읽어야 한다 — "0.1초 간격 연타"는 동시성 유형이지만 실제로는 순차 클릭이고, "요청 직후 F5"는 중단·이탈 유형이지만 `page.reload()` 로 재현된다.

## 용어

| 표기 | 원어 | 뜻 |
|---|---|---|
| e2e | end-to-end | 실제 브라우저로 사용자 흐름 전체를 검증하는 시험 |
| 판별력 | mutation detection | 시험이 실제로 결함을 잡아내는 능력. 통과만으로는 증명되지 않는다 |

## 증상

- 시나리오 수천 행을 훑고 나온 "자동화 불가" 비율이 비정상적으로 높다(70% 이상).
- 불가로 분류된 행을 무작위로 몇 개 열어 보면 대부분 그냥 클릭 순서다.
- 그 목록을 그대로 별도 통합시험 과제로 넘기면, 넘겨받은 쪽이 다시 판정하느라 같은 일을 두 번 한다.

## 원인

유형 열은 **원인을 분류한 이름**이지 **조작 난이도**가 아니다. 그런데 대량 판정에서는 행 본문을 다 읽는 비용이 커서 유형 열로 일괄 처리하고 싶어진다. 그 순간 이름이 판정을 대신한다.

- **"동시성"** — 진짜 동시 도달을 요구하는 것과, 사람 손으로 빠르게 두 번 누르는 것이 같은 이름 아래 섞여 있다. 후자는 순차 조작이다.
- **"중단·이탈"** — 프로세스를 죽이는 것과 페이지를 새로고침하는 것이 같은 이름이다. 후자는 API 하나다.
- **"순서 이상"** — 단순히 화면을 다른 순서로 밟는 것이 대부분이다.

## 해결

**2단계 판정**으로 간다.

1. **1차(유형 열)**: 후보를 좁히는 데만 쓴다. 결과를 판정으로 확정하지 않는다.
2. **2차(조작 내용)**: 1차에서 불가로 묶인 것을 전부 다시 읽고, 아래 세 가지에 해당할 때만 진짜 불가로 남긴다.

| 진짜 불가 | 왜 | 필요 수단 |
|---|---|---|
| 타이밍 정밀 제어 | 서버 도달 순서를 제어해야 한다 | 서버측 경합 결정화, 통합시험 계층 |
| 브라우저 밖 조작 | 프로세스 강제 종료·네트워크 단절 | 프록시 장애 주입, `tc netem`, 프로세스 kill |
| 서버 셸 | 파일 권한 조작·심볼릭 링크 교체 | 서버 접근 |

- **UI 로 못 하는 것과 도구로 못 하는 것을 가른다.** 화면에 버튼이 없어도 API 직접 호출로 도달하면 자동화 가능이다.
- 판정 결과에 **행별 근거를 남긴다.** 근거 없는 판정은 다음 사람이 처음부터 다시 한다 — 실제로 이 재판정에서 824건이 되살아났다.
- 통과로 판정한 대량 건은 그것대로 위험하다. **판별력이 검증되지 않은 시험**은 별도로 세어 두고, 통과 자체를 근거로 쓰지 않는다.
- 재판정으로 범위가 커진 이슈가 있으면 **먼저 알린다.** 진행 중인 수정이 옛 범위로만 짜여 있으면 남는 경로가 생긴다.

> [!WARNING]
> 1차 판정 수치를 보고 상위에 보고하면 그 숫자가 계획이 된다. 재판정으로 한 자릿수 %까지 떨어질 수 있으므로, 1차는 **잠정**임을 명시해서 내보낸다.
