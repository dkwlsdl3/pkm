# 뮤테이션으로 테스트 실효성을 확인한다

> **TL;DR**: 테스트가 green인 것은 "구현이 맞다"가 아니라 **"이 테스트가 실패하지 않았다"**일 뿐이다. 검증하려는 구현을 **일부러 되돌려(mutate) 그 테스트가 실제로 FAIL하는지** 확인하고, 확인 후 원복한다. 되돌려도 통과하는 테스트는 장식이다.

---

## 왜 필요한가

테스트 수백 개가 green인데도 결함이 살아남는 일이 실제로 생긴다. 원인은 대개 테스트가 **구현이 아니라 구현의 그림자**를 검사하기 때문이다.

## 되돌려도 통과하는 테스트의 전형

| 유형 | 예 | 왜 무의미한가 |
|---|---|---|
| **문자열 검사** | 생성된 SQL에 `"FOR UPDATE"` substring이 있는지 확인 | 쿼리 문자열은 그대로인데 실행 경로가 빠져도 통과 |
| **test-only 헬퍼 검사** | `#[cfg(test)]` 헬퍼의 반환값만 단정 | 프로덕션 경로와 다른 코드를 검증 |
| **상수 자체 검사** | `MODE == 0o600`인지 확인 | **호출 지점**의 값을 `0o644`로 되돌리면 그냥 통과 |
| **개수만 세는 검사** | 재연결 시도가 10회를 넘지 않는지 | 예산이 매 회차 리셋되는 구현도 통과(무한 재연결인데 각 구간은 10회 이하) |
| **빈 픽스처** | 부가 조건 배열을 **항상 `&[]`**로 세팅 | 그 축을 읽는 코드가 아예 없어도 green |
| **vacuous 단정** | 두 경우가 다른 경로로 같은 결과에 수렴 | 무엇을 구분하는지 증명하지 않음 |

## 방법

1. 검증 대상 구현을 **한 지점만** 되돌린다(가드 제거, 조건 반전, 기본값 0으로, 상수 되돌리기)
2. 해당 테스트를 돌려 **FAIL을 확인**한다
3. 원복하고 전체 green 복귀 + 잔재 0을 확인한다
4. FAIL하지 않았다면 **테스트를 고친다**(구현이 아니라 테스트가 문제다)

```
# 예: 권한 상수를 되돌려 확인
- const BACKUP_FILE_MODE: u32 = 0o600;
+ const BACKUP_FILE_MODE: u32 = 0o644;
→ 기대: "group/other 비트가 0" 불변식 테스트 FAILED
```

## 테스트를 고치는 방향

- **문자열 → 실제 동작**: SQL substring 검사를 임시 DB에 실제 경쟁 트랜잭션을 붙이는 통합 테스트로 교체
- **개수 → 경계값**: "10회 이하"가 아니라 **지연 경계를 직접 재라**(예: 1,999ms vs 1ms)
- **상수 → 불변식**: 상수 값 비교가 아니라 "group/other 비트가 0" 같은 **성질**을 검사
- **표에서 런타임 열거**: 픽스처를 손으로 채우지 말고 정책 표를 순회해 검사하면 **새 항목이 자동으로 커버**된다
- **기본값 전용 테스트를 따로 둔다**: 실제 소비자가 옵션을 넘기지 않고 기본값에 의존하면, 기본값을 꺼도 아무도 못 잡는다

## 함께 기억할 "green인데 안 돈 것" 3종

1. **테스트가 조용히 skip됐다** — `#[ignore]` 통합 테스트를 `-- --ignored` 없이 돌리면 `N ignored`로 넘어가는데 요약만 보면 통과로 읽힌다
2. **테스트가 구현을 되돌려도 통과한다** — 위의 모든 유형
3. **서비스가 옛 바이너리로 돌고 있다** — 코드는 고쳤지만 재빌드·재배포가 안 된 상태

세 번째까지 포함해 "green"을 의심하는 습관이 필요하다.

## 스모크 테스트에도 같은 원리

화면 스모크에 "없는 경로"를 넣는 뮤테이션이 **잡히지 않은** 사례가 있다 — 404 화면도 제목이 있고 URL도 그대로여서 백지·리다이렉트 검사를 전부 통과했다. 즉 페이지가 삭제·개명돼도 초록으로 남는 구멍이었고, **404 판별을 별도 검사로 추가한 뒤에야** 뮤테이션이 잡혔다.
