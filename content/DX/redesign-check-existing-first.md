# 기존 앱 재설계 착수 원칙 — 먼저 기존 구현 확인

> 화면/기능 재설계(리뉴얼)에서 새로 만들기 전에 **반드시 기존 구현을 검색**한다.

## 문제 상황
설계변경 문서(전/후 비교)를 받고 화면들을 "새 목업"으로 다 만들었더니, 상당수가 **이미 실제로 동작하는 기존 페이지를 중복**했다. 재설계는 대개 **재편(이동/수정)** 이지 **재작성** 이 아니다.

## 원칙
1. 스펙의 각 항목 태그를 먼저 읽는다: **추가**(신규) / **수정** / **이동** / **뷰 변경**.
2. **수정·이동** → 기존 실제 페이지가 있다. 그 데이터 연동을 살려 **재배치/재스타일**. 새 mock 금지.
3. **추가** 만 신규 제작.
4. 착수 전 "기존 페이지·서비스 검색"을 **필수 게이트**로 둔다. (파일명 + 서비스 import로 실제/목업 구분 → [[detect-page-backend-wiring]])

## 비용
이 확인을 건너뛰면: 토큰·시간 낭비 + 실기능을 가짜로 덮는 위험 + 롤백 필요. 특히 멀티에이전트로 병렬 생성하면 중복이 배로 늘어난다.
