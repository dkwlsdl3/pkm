# 상보 조건의 죽은 분기 탐지

> **TL;DR**: `v-if`/`v-else`처럼 상보적인 분기에서 **한쪽 조건이 데이터상 절대 발생하지 않으면**, 반대편 분기와 그 분기만 쓰던 헬퍼·i18n 키는 도달 불가능한 죽은 코드다. 데이터 계약(DB CHECK, 백엔드 enum)을 기준으로 가능한 값 집합을 좁혀 가지치기한다.

---

## 개요

- **무엇인가**: UI 조건 분기 중 실제 데이터로는 도달 불가능한 코드를 찾아 제거하는 리팩터링 휴리스틱
- **왜 쓰는가**: 죽은 분기는 읽는 사람을 오도하고("owner 케이스가 있나 보다"), 유지보수 비용만 늘린다
- **언제 쓰는가**: 역할/상태 같은 **닫힌 값 집합(enum)**을 다루는 화면을 정리할 때

---

## 핵심 개념

### 추적 순서 (데이터 계약 → UI)

1. **가능한 값 집합 확정**: 백엔드 검증(`valid_roles = ["leader","member"]`)과 DB 제약(`CHECK (role IN ('leader','member'))`)을 보고 실제 저장 가능한 값을 확정.
2. **주입 지점 확인**: 프론트/백엔드 어디서도 그 외 값(예: `owner`)을 만들지 않는지 확인.
3. **도달 불가 분기 식별**: `v-else`/`v-if="x === 'owner'"`처럼 불가능한 값에만 반응하는 분기.
4. **연쇄 제거**: 죽은 분기 + 그 분기만 호출하던 헬퍼(`getMemberRoleVariant` 등) + 고아 i18n 키까지 함께 제거.

### 흔한 형태

- `v-if="role !== 'owner'"` 가드 — `owner`가 불가능하면 **항상 참** → 가드 제거.
- `owner`용 `<Chip>`/배지 분기 — 도달 불가 → 삭제.
- 삭제로 미사용이 된 헬퍼 함수·번역 키 → 함께 삭제 (Select가 하드코딩 라벨을 쓰면 i18n 키는 고아가 됨).

### 검증

```bash
pnpm exec eslint        # 0 errors (미사용 변수/함수 경고 정리 포함)
# Playwright로 실제 화면에 의도한 옵션만 노출되는지 확인
```

## 주의사항

> [!WARNING]
> "혹시 나중에 쓸지 모르니 남겨두자"의 유혹을 경계할 것. 재추가가 **국소적**(한 곳에 옵션·라벨 추가)이라면, 도달 불가능한 죽은 코드를 안고 가는 것보다 제거가 낫다. 단, 제거 전에 반드시 1~2단계(데이터 계약·주입 지점)로 "정말 불가능한지"를 확인한다.
