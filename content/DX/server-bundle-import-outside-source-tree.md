# 서버 코드가 소스 트리 밖 모듈을 가져오면 개발 모드만 깨진다

> **TL;DR**: 서버 라우트가 `../../utils/foo` 로 **클라이언트 쪽 파일**을 가져왔다. 그 상대 경로는 **디스크상 맞다 — 틀린 적이 없다.** 문제는 그 파일이 **서버 빌드의 소스 트리 밖**이라는 것. 개발 모드 번들러는 그것을 자기 소스로 보지 않고 외부 모듈로 내보내면서 **출력 파일 기준으로 상대 경로를 다시 쓰고**, `../` 가 파일시스템 루트를 넘어가 서버 번들이 못 뜬다 → **앱 전체 500**. 프로덕션 빌드·단위시험·정적 검사는 **전부 통과한다.** 동작이 아니라 **경계**를 보는 검사가 필요하다.

## 증상

- 개발 서버를 띄우면 페이지 하나가 아니라 **앱 전체가 500**
- 오류 메시지가 `/utils/websocketClose` 처럼 **파일시스템 루트에 붙은 경로**를 못 찾는다고 말한다
- ⚠️ `../` 개수가 실제 위치와 무관하게 고정이라, 저장소를 다른 깊이에 두면 **오류 경로만 달라지고 증상은 같다**
- **프로덕션 빌드는 성공한다** — 그래서 "빌드가 되는데 왜 안 뜨지"로 시작한다

## 원인

번들러는 소스 트리(서버 엔트리에서 도달 가능한 자기 소스 집합)를 기준으로 모듈을 가른다.

- **트리 안**의 파일 → 번들에 포함하거나 청크로 쪼갠다
- **트리 밖**의 파일 → "외부 모듈"로 판단하고 import 문을 **그대로 남긴다.** 그런데 출력 파일 위치는 소스 위치와 다르므로, 상대 경로를 **출력 기준으로 다시 계산**한다

이때 계산이 원본의 깊이를 그대로 반영하면 `../` 가 과도하게 붙고 루트를 넘는다. 결과는 존재할 수 없는 경로다.

**왜 아무것도 못 잡았나** — 이 결함의 성질이 여기 있다.

| 검사 | 왜 통과했나 |
|---|---|
| 단위시험 | 시험 러너가 `~`·`@` 별칭을 **자기 설정으로** 푼다 → **빌드와 다른 규칙으로 모듈을 찾는다.** 게다가 서버 라우트는 어떤 시험도 안 불러온다 |
| 정적 검사 (ESLint 등) | 경로가 **디스크상 맞으므로** 볼 것이 없다 |
| 프로덕션 빌드 | 같은 파일을 **청크로 정상 번들**한다. 빌드를 돌려도 안 잡힌다 |
| 타입 검사 | 파일이 실재하므로 타입도 맞다 |

즉 **동작을 확인하는 어떤 검사로도 잡히지 않는다.** 개발 모드에서 실제로 띄워야만 드러난다.

## 해결

**경계를 보는 검사를 넣는다** — 서버 코드가 자기 트리 밖을 **상대 경로나 클라이언트 별칭으로** 가리키면 실패시킨다.

```js
// 서버 소스 트리 안의 모든 파일을 훑어, 트리 밖으로 나가는 import 를 금지
// 검사 대상: '../' 로 트리를 벗어나는 상대 경로, 클라이언트 전용 별칭('~/', '@/')
```

그리고 문제의 파일 자체는 **서버 소스 트리 안으로 옮긴다.**

- 번들러 설정으로 예외를 주는 방법도 있지만, 그러면 **왜 그 파일만 예외인지가 어디에도 안 남는다**
- 그 유틸을 클라이언트가 정말 안 쓰는지 먼저 확인한다. 서버 라우트와 자기 시험만 쓴다면 이동이 정답이다

## 교훈

같은 디렉터리에 있던 다른 유틸은 **무관했다** — 클라이언트와 자기 시험만 쓰고 서버 번들에 아예 없었다. "옆 파일도 위험해 보인다"로 범위를 넓히기 전에 **누가 그 파일을 실제로 가져가는지**부터 세라.
