# 「이미 있으면 건너뛴다」가 설치 재실행에서 구성 보장을 통째로 날린다

> **TL;DR**: 설치 스크립트의 각 블록이 **명령·바이너리의 존재**로 통째로 갈라지면, 그 블록 안에 있던 사용자 생성·설정 편집·유닛 등록·기동까지 함께 건너뛴다. 재실행하면 "설치는 됐는데 구성이 안 된" 상태가 그대로 남는다. **설치와 보강(ensure)을 분리해서**, 보강은 분기 밖에서 언제나 돌게 해라. 반대로 **덧붙이기(append)에는 가드가 필요하다** — 재실행마다 같은 설정이 쌓인다.

## 증상

- 설치를 다시 돌렸는데 여전히 설정이 반영돼 있지 않다. 로그에는 "이미 설치됨"만 찍힌다.
- 계정은 이미 있는데 그 계정이 필요한 그룹(`wheel` 등)에 안 들어가 있다.
- 반대로 설정 파일 끝에 같은 블록이 **두 번, 세 번 쌓여** 있다.
- 재실행할 때마다 원본 백업이 **이미 수정된 파일로 덮여** 원본이 사라진다.

## 원인

두 가지 실수가 짝을 이룬다.

**① 존재 검사가 블록 전체를 감싼다.** `command -v zfs` 나 바이너리 존재로 블록을 건너뛰는데, 그 블록 안에는 설치만 있는 게 아니라 사용자·디렉터리·설정 편집·유닛·기동이 함께 들어 있다.

```bash
if ! command -v grafana-server >/dev/null; then
    dnf install -y grafana
    edit_grafana_ini          # ← 재실행에서 통째로 건너뛴다
    systemctl enable --now grafana-server
fi
```

**② 덧붙이기에 가드가 없다.** `cat >> postgresql.conf` 같은 블록이 두 번 돌면 같은 설정이 파일 끝에 쌓인다.

## 해결

**설치 경로와 보강 경로를 나눈다.** 보강 함수는 대상이 없으면 아무것도 하지 않고, 있으면 구성을 맞춘다. 그리고 **정상 경로에서도 보강을 부른다.**

```bash
install_if_missing_grafana        # 없을 때만 설치
ensure_grafana_config             # 🔴분기 밖 — 언제나 돈다
```

새 보강을 추가할 때 **그 함수 하나만 고치면 되게** 만드는 것이 요점이다. 호출 지점 셋을 각각 고치는 형태였다면 하나가 빠진다.

**덧붙이기에는 마커 가드를 둔다.**

```bash
grep -q "$PG_CUSTOM_SETTINGS_MARKER" "$PG_CONF" || cat >>"$PG_CONF" <<EOC
$PG_CUSTOM_SETTINGS_MARKER
...
EOC
```

**그룹·권한 보강은 계정 생성 분기 밖으로 뺀다.** 계정이 이미 있으면 그룹 보강까지 건너뛰던 것이 이 계열의 전형이다. 다만 **비밀번호는 다루지 않는다** — 기존 계정의 자격증명을 덮으면 안 된다.

## 주의

> [!WARNING]
> **무조건 `cp` 로 백업하지 마라.** 재실행마다 백업을 뜨면 **이미 수정된 파일이 원본 백업을 덮어써 원본이 사라진다.** 백업은 백업이 없을 때만 뜬다.

> [!WARNING]
> **설정 파일을 정규식으로 편집할 때는 주석 줄과 활성 줄을 구별해라.** `;allow_embedding = false` 만 매치하도록 써 두면 주석의 값이 다른 경우를 놓친다. 패턴 앞에 `^` 를 붙여 **활성 줄만** 세지 않으면, 주석 줄을 세어 필요한 삽입을 건너뛴다.

> [!NOTE]
> **이미 로드된 유닛은 덮어쓰지 않는다.** 바이너리 공급자가 둘일 수 있다(직접 배치한 것과 패키지가 준 것). 우리 유닛으로 덮으면 패키지 쪽 갱신 경로가 끊긴다.

> [!NOTE]
> **보안 정책은 보강 대상이 아니다.** 익명 접근처럼 관리자가 일부러 꺼 둔 설정을 재실행이 되살리면 안 된다.
