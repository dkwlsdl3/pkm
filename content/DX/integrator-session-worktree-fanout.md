# 통합 세션 + 격리 워크트리로 에이전트 세션 병렬화하기

> **TL;DR**: 에이전트 세션을 여럿 돌릴 때 한 워크트리를 공유하면 커밋이 서로 섞인다. **작업 세션마다 격리 워크트리를 주고**, 세션 하나를 **통합 관제**로 지정해 배분·머지·공용 문서 커밋만 맡기면 충돌 없이 병렬화된다. 관건은 세션 유형별로 **금지 규칙을 프롬프트에 못 박는 것**이다.

## 왜 이 구조인가

한 워크트리를 여러 세션이 공유하면 경로 지정 커밋도 옆 세션의 미커밋 변경을 함께 담고, 트리 전체를 되돌리는 명령이 남의 작업을 날린다([[shared-worktree-parallel-agents]]). 그렇다고 세션을 하나만 쓰면 서로 독립인 작업까지 직렬로 처리된다.

해법은 **격리 + 단일 머지 지점**이다.

```text
통합 관제 세션 (코드를 쓰지 않는다)
  ├─ 할 일 목록·브리핑 문서를 읽고 서로 독립인 묶음으로 분할
  ├─ W1..Wn 배분
  ├─ 각 세션 결과를 [MOD] ... 머지 커밋으로 병합
  └─ 공용 문서(할 일 목록·설계 문서) 커밋은 여기서만

W1  격리 워크트리   백엔드
W2  격리 워크트리   백엔드
W3  격리 워크트리   프론트 전용
W4  공유 트리       실서버 실증 / 조사 전용 (코드 수정 없음)
```

## 배분 규칙

### 1. 세션 유형마다 금지 사항을 명시한다

역할만 주면 세션은 "도움이 되려고" 경계를 넘는다. **하지 말 것**을 함께 적어야 한다.

| 유형 | 워크트리 | 명시해야 할 금지 |
|---|---|---|
| 백엔드 구현 | 필수 | 다른 세션 소유 파일 수정 금지, 서비스 재시작 금지 |
| 프론트 전용 | 필수 | **빌드 도구 실행 금지**(백엔드 파일은 읽기만) |
| 실서버 실증 | 불필요 | 코드 수정 금지, 결함은 보고만 |
| 조사 전용 | 불필요 | **코드를 한 줄도 고치지 마라**, 산출물은 문서와 보고뿐 |

⚠️ 프론트 세션에 컴파일 금지를 거는 건 취향이 아니라 **자원 제약**인 경우가 많다. 컴파일 캐시가 큰 언어(Rust 등)는 세션 수만큼 빌드 캐시가 불어나 그것만으로 디스크가 찬다.

### 2. 확인하는 세션과 고치는 세션을 분리한다

실화면 확인 세션에는 **"결함을 찾으면 고치지 말고 보고해라 — 착수는 통합 세션이 배분한다"** 를 넣는다. 확인하던 세션이 그 자리에서 고치기 시작하면 어느 커밋이 검증된 것인지 알 수 없게 되고 머지 순서가 엉킨다.

### 3. 워크트리는 연 세션이 닫는다

- 열어둔 채 세션이 끝나면 다음 사람이 **누구 것인지 모르는 워크트리**를 마주한다
- 닫기 전에 **자기 커밋이 머지된 것을 확인**하게 한다. 머지 전에 닫으면 작업이 사라진다
- 통합 세션이 먼저 사라졌을 경우의 대비도 프롬프트에 넣는다(보고를 커밋 메시지에 담고 종료 등)

### 4. 배분 단위는 "서로 독립"이 유일한 기준이다

같은 파일을 건드릴 두 묶음은 아무리 작아도 한 세션에 준다. 파일 단위로 소유권이 갈리지 않으면 머지에서 그 이득을 전부 반납한다.

## 이 구조의 한계

- **통합 세션이 병목**이다. 머지와 문서 커밋이 한 곳에 몰리므로 세션 수를 늘려도 어느 지점부터는 처리량이 안 는다
- 배분 프롬프트를 쓰는 비용이 작지 않다. 배경·금지 사항·완결 기준을 매번 적어야 하므로 **한 세션이 몇 시간짜리 일을 맡을 때** 수지가 맞는다. 10분짜리 작업을 쪼개 배분하면 손해다
- 각 세션은 다른 세션이 무엇을 고쳤는지 모른다. **같은 결함을 두 세션이 다르게 고치는 일**이 생기므로, 머지 시점에 통합 세션이 겹침을 확인해야 한다
