# 모노레포 vs 멀티레포

> **TL;DR**: 여러 서비스를 하나의 레포에서 관리(모노레포) vs 각각 분리(멀티레포) — 대형 솔루션엔 모노레포, 독립 서비스엔 멀티레포

---

## 개념 비교

```
모노레포 (Monorepo)          멀티레포 (Polyrepo)
┌──────────────────┐         ┌────────┐ ┌────────┐
│  my-project/     │         │ svc-a/ │ │ svc-b/ │
│  ├── frontend/   │         └────────┘ └────────┘
│  ├── backend/    │         ┌────────┐ ┌────────┐
│  ├── ai-engine/  │         │ svc-c/ │ │ svc-d/ │
│  └── packages/   │         └────────┘ └────────┘
└──────────────────┘
```

---

## 장단점 비교

| 항목 | 모노레포 | 멀티레포 |
|------|---------|---------|
| **코드 공유** | 쉬움 (직접 임포트) | 어려움 (npm 패키지 배포 필요) |
| **버전 관리** | 전체 일관성 유지 용이 | 서비스별 독립 버전 |
| **빌드 시간** | 전체 빌드 느림 (캐싱 필수) | 서비스별 빠름 |
| **변경 영향 파악** | 한 PR로 전체 파악 | 서비스 간 추적 어려움 |
| **팀 자율성** | 낮음 (공유 규칙 필요) | 높음 |
| **CI/CD 복잡도** | 높음 | 낮음 |
| **git 클론 속도** | 느림 | 빠름 |

---

## 모노레포를 선택해야 할 때

- 여러 서비스가 **공유 코드를 자주 리팩토링**하는 경우
- **버전 일관성**이 중요한 대형 솔루션 (통합 릴리스)
- CI/CD, 린팅, 테스트 등 **도구 통합**이 필요한 경우
- 2025년 기준 50명 이상 개발 조직의 63%가 모노레포 사용

## 멀티레포를 선택해야 할 때

- 서비스 간 **완전한 독립 배포**가 필요한 경우
- 팀별 **기술 스택이 다른** 경우
- 소규모 독립 서비스 다수 운영

---

## Git 서브모듈 방식 (keeper-gen-2 사례)

모노레포의 변형 — 루트 레포가 각 서비스를 서브모듈로 관리:

```
keeper-gen-2/           ← 루트 레포 (통합 관리)
├── .gitmodules
├── version.yaml        ← 전체 버전 일관성 관리
├── packaging/          ← RPM 메타 패키지
├── backend/            ← 서브모듈 (독립 레포)
├── frontend/           ← 서브모듈
└── ai-engine/          ← 서브모듈
```

- **장점**: 각 서브모듈은 독립 레포로 자체 히스토리 보유
- **단점**: 서브모듈 포인터 수동 업데이트 필요, 초보자에게 복잡함

## 모노레포 도구

### Turborepo (Vercel)

```bash
npx create-turbo@latest
```

- 기존 레포에 10분 내 적용 가능, 즉각적인 빌드 속도 개선
- package.json 스크립트 기반 — 프로젝트 구조 변경 불필요
- **약점**: 아키텍처 강제 없음, 순환 의존성 방지 미지원

### Nx

```bash
npx create-nx-workspace@latest
```

- 코드 생성, 아키텍처 규칙, 의존성 그래프 시각화 내장
- 멀티 언어 지원 (JS/TS, Java, Python, Go, Rust)
- **2025년 코어를 Rust로 마이그레이션** — 속도 대폭 향상
- **약점**: 설정 복잡, 기존 프로젝트 마이그레이션 난이도 높음

### 선택 기준

| 상황 | 권장 |
|------|------|
| 빠르게 도입, JS/TS 팀 | Turborepo |
| 복잡한 대형 모노레포, 혼합 기술 스택 | Nx |
| 구글/메타 규모 | Bazel |
