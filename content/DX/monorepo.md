# 모노레포 vs 멀티레포

> **TL;DR**: 여러 서비스를 하나의 레포에서 관리(모노레포 = 싱글레포) vs 각각 분리(멀티레포) — 대형 솔루션엔 모노레포, 독립 서비스엔 멀티레포. ★**Git 서브모듈로 묶은 구조는 모노레포가 아니라 멀티레포 + 메타 레포다**(자주 틀리는 지점).

---

## 개념 비교

```
모노레포 (Monorepo)          멀티레포 (Polyrepo)
┌──────────────────┐         ┌────────┐ ┌────────┐
│  my-project/     │         │ svc-a/ │ │ svc-b/ │
│  ├── frontend/   │         └────────┘ └────────┘
│  ├── backend/    │         ┌────────┐ ┌────────┐
│  ├── ai-engine/  │         │ svc-c/ │ │ svc-d/ │
│  └── packages/   │         └────────┘ └────────┘
└──────────────────┘
```

---

## 장단점 비교

| 항목 | 모노레포 | 멀티레포 |
|------|---------|---------|
| **코드 공유** | 쉬움 (직접 임포트) | 어려움 (npm 패키지 배포 필요) |
| **버전 관리** | 전체 일관성 유지 용이 | 서비스별 독립 버전 |
| **빌드 시간** | 전체 빌드 느림 (캐싱 필수) | 서비스별 빠름 |
| **변경 영향 파악** | 한 PR로 전체 파악 | 서비스 간 추적 어려움 |
| **팀 자율성** | 낮음 (공유 규칙 필요) | 높음 |
| **CI/CD 복잡도** | 높음 | 낮음 |
| **git 클론 속도** | 느림 | 빠름 |

★ **"빌드 시간"과 "독립 배포"는 실측으로 완화 확인.** 사내 전환 사례에서 우려했던 두 항목이 실제로는 발생하지 않았다 — CI에 컴포넌트별 경로 필터(`rules:changes`)를 걸면 **변경된 컴포넌트만** 빌드·배포하고, 컴포넌트별 배포 잡을 그대로 유지하면 독립 배포도 살아 있다. 실제로 문제가 된 건 통합 자체가 아니라 **한 컴포넌트만 배포 잡이 누락된 비대칭**이었다.

---

## 모노레포를 선택해야 할 때

- 여러 서비스가 **공유 코드를 자주 리팩토링**하는 경우
- **버전 일관성**이 중요한 대형 솔루션 (통합 릴리스)
- CI/CD, 린팅, 테스트 등 **도구 통합**이 필요한 경우
- 2025년 기준 50명 이상 개발 조직의 63%가 모노레포 사용

## 멀티레포를 선택해야 할 때

- 서비스 간 **완전한 독립 배포**가 필요한 경우
- 팀별 **기술 스택이 다른** 경우
- 소규모 독립 서비스 다수 운영

---

## Git 서브모듈 방식 — 모노레포가 아니다

★ **가장 흔한 용어 오류.** 루트 레포가 서비스들을 서브모듈로 묶은 구조를 "모노레포"나 "모노레포의 변형"이라 부르는 문서가 많은데, **틀렸다.** 이건 **멀티레포 + 메타(aggregator) 레포**다.

```
<project-root>/         ← 메타 레포 (포인터만 보유)
├── .gitmodules         ← 서브모듈 정의
├── version.yaml
├── packaging/          ← RPM 메타 패키지
├── backend/            ← gitlink (mode 160000) → 별개 레포
├── frontend/           ← gitlink → 별개 레포
└── ai-engine/          ← gitlink → 별개 레포
```

**왜 모노레포가 아닌가**

| | 서브모듈 방식 | 모노레포 |
|---|---|---|
| 레포 개수 | 컴포넌트마다 **독립 레포** | **1개** |
| 루트에 들어가는 것 | 커밋 SHA **포인터**(gitlink, mode `160000`) | 실제 파일 |
| 히스토리 | 레포별로 분리 | **단일 커밋 그래프** |
| 원자적 변경 | **불가** — 컴포넌트별 커밋 + 포인터 갱신 커밋 | 가능 — 한 커밋으로 |

모노레포의 정의는 *하나의 레포·하나의 히스토리·하나의 커밋 그래프*다. 서브모듈은 통합된 것처럼 **보이기만** 한다.

- **장점**: 각 서브모듈이 자체 히스토리를 보유. 레포별 접근 권한 분리 가능
- **단점**: 포인터 수동 갱신, 원자적 변경 불가, `--recursive` 누락 시 빈 디렉터리, 초보자에게 복잡

> **용어 정리**: **싱글레포는 모노레포와 같은 말**이다. 별개의 제3 전략이 아니다. "모노레포인데 싱글레포로 전환"처럼 쓰면 문장이 성립하지 않는다.

### 사내 프로젝트 이력

서브모듈 9개 구성으로 운영하다가 **2026-07에 진짜 모노레포로 전환 완료**(단일 레포·단일 히스토리, `.gitmodules` 없음). 구 레포는 push 중단·조회 전용으로 격하했다. 전환 절차는 아래 체크리스트 참고.

## 서브모듈에서 진짜 모노레포로 전환할 때 체크리스트

서브모듈 기반 레포를 새 모노레포로 옮길 때는 단순히 파일을 한곳에 복사하는 것만으로 끝나지 않는다.

- **정본 선언**: 새 remote/branch/cwd를 명확히 선언하고, 기존 레포는 archive 또는 read-only로 격하시킨다.
- **gitlink 제거 검증**: `.gitmodules`가 없고 `git submodule status --recursive`가 비며, `git ls-files -s`에 mode `160000`이 남지 않아야 한다.
- **CI 단일화**: 컴포넌트별 CI 파일을 루트 파이프라인으로 통합하고, job 이름은 `component:job`처럼 네임스페이스를 둔다.
- **범위 밖 레포 분리**: 한 번에 다 옮기지 않는 서비스는 "없는 디렉터리"가 아니라 "외부 레포/패키지 입력물"로 문서화한다.
- **문서 현재화**: README, agent brief, release guide, CI docs, structure map에서 `--recursive`, `git submodule update`, root pointer 같은 표현을 제거한다.
- **구레포 안전장치**: 기존 repo에는 push 중단, 조회 전용, 새 정본 링크를 남겨 다음 agent가 잘못된 곳에서 작업하지 않게 한다.

전환 당일에는 코드보다 문서가 더 위험하게 낡는다. 특히 AI agent가 읽는 `AGENTS.md`, `CLAUDE.md`, `docs/agent-brief.md`, `TODO.md`는 새 정본을 가리키는지 먼저 확인한다.
