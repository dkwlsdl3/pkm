# 오탐을 피하려 좁힌 정적 규칙은 원래 버그를 놓친다

> **TL;DR**: 오탐이 싫어 lint 규칙의 조건을 좁히면, 좁힌 틈이 대개 **고치려던 버그의 원형**이다. 오탐의 원인을 먼저 규칙 밖으로 걷어내고, 규칙은 전면 금지로 건다. 넓혔을 때 새로 드러나는 위반 수가 좁은 규칙이 놓치던 양이다.

## 증상

- 재발 방지 규칙을 넣고 위반 0건을 확인했는데, 같은 유형의 결함이 계속 나온다
- 교차검증에서 「이 규칙은 X 형태를 못 잡는다」는 지적이 나온다

## 원인

실제 사례: 날짜 `toLocaleString` 호출을 막는 규칙을 만들면서, 같은 메서드를 쓰는 **숫자 천 단위 포맷이 오탐으로 걸리자** 조건을 `new Date(...).toLocaleString()` 직접 체인으로 좁혔다.

```js
const d = new Date(v)
d.toLocaleString('ko-KR')   // 변수에 담은 Date — 좁힌 규칙을 통과
```

그런데 고치려던 화면 중 여럿이 정확히 이 형태였다. 여기에 규칙이 `<script>` 만 보는 구멍까지 겹쳐, 규칙을 전면 금지로 넓히자 **위반 20건이 새로 드러났다**.

## 해결

1. **오탐 원인을 먼저 걷어낸다** — 숫자 포맷을 전용 유틸(`formatCount`)로 옮기고, 그 파일 한 곳만 규칙 예외로 둔다
2. **규칙은 메서드 이름 기준 전면 금지**로 건다(수신자 형태를 따지지 않는다)
3. **넓힌 직후 위반 수를 센다** — 그 숫자를 커밋·노트에 남겨, 다음에 누가 다시 좁히려 할 때 근거로 쓴다
4. 규칙 옆 주석에 「좁히지 마라 — 좁혔다가 뚫린 형태 두 가지」를 적는다

> [!NOTE]
> 「사람이 grep 으로 세서 전부 고쳤다」도 같은 실패를 한다. 다른 이름이나 인라인으로 박힌 사본은 이름 검색에 안 걸린다. 셀 것이 아니라 막을 것이다.
